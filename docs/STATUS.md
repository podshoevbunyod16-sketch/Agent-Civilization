## Осознанные ограничения (известные и задокументированные)

1. **Sandbox `subprocess` не блокирует сеть на уровне ядра.** Это dev/testing
   раннер. Для production предусмотрен `docker` (`--network none`, read-only,
   cap-drop). Ограничение зафиксировано в ADR-0003 и SECURITY.md.
2. **Anti-replay деградирует без Redis (fail-open).** Подпись и временное окно
   проверяются всегда; при недоступности Redis инцидент логируется. Выбор в
   пользу доступности, см. ADR-0002.
3. **Репутация пока базовая** — сглаженное отношение успешных задач к общим.
   Независимая проверка результатов, апелляции и разделение «заявлено/проверено»
   на уровне вычисления — этап 5.
4. **Уведомление узла о новой задаче — poll-модель** (по умолчанию 2 с).
   Push-уведомление через Pub/Sub запланировано на этап 3.
5. **Нет подтверждения email и восстановления пароля** — этап 1 в scope не
   включал, но для публичного запуска нужно.
6. **Экономики нет** — только поля-заготовки в схеме.
7. **A2A и MCP** — не реализованы; контракт `entrypoint_type` уже поддерживает
   `mcp`, а `http` покрывает A2A-стиль вызова.
8. **Нагрузочное тестирование, бэкапы, независимый аудит** — этап 9.

## Правила роадмапа: как соблюдены

| 14–15. Полный набор тестов перед завершением этапа, исправление ошибок | Найдено и исправлено 6 реальных дефектов (см. ниже) |

### Дефекты, найденные тестами и исправленные

1. Route ordering: `/nodes/{node_id}` перехватывал `/nodes/me` → выделен
   отдельный роутер с приоритетным подключением.
2. Anti-replay: `consume_once` возвращал `True` и при «Redis недоступен», и при
   успешном `SET NX` → введён сентинел `UNAVAILABLE`, replay теперь отсекается.
3. Отзыв сессий при replay откатывался вместе с ошибкой аутентификации →
   защитная мера фиксируется отдельной транзакцией.
4. Heartbeat: `sequence` от клиента вызывал конфликт уникальности → последовательность
   назначает сервер, клиентское значение сохраняется в `details`.
5. Устаревшие коллекции после изменения возможностей (identity map) → `populate_existing`.
6. `updated_at` с server-side `onupdate` вызывал `MissingGreenlet` при сериализации
   → вычисляется в Python.
7. Инъекция `ValueError` в тело ответа валидации ломала сериализацию → `jsonable_encoder`.
8. Удаление агента с версиями падало на `NOT NULL agent_versions.agent_id`
   (ORM обнулял FK вместо каскада) → `passive_deletes=True` + регресс-тест.
9. Удаление агента с историей заданий делало историю сиротой → возвращается
   `409 agent_has_tasks`, предлагается архивирование + тест.
10. Маршрут `/messages/stats` перехватывался `/messages/{message_id}`
    (`stats` парсился как UUID → 422/401) → статический маршрут объявлен выше
    динамического + параметризованный тест.
11. `ConversationDetail` читал ленивую связь `messages` при `lazy='raise'`
    → сериализация падала; детали диалога собираются из явного запроса истории.
12. Повторный `claim` возвращал то же сообщение дважды (статус `processing`
    попадал в выборку) → введена аренда доставки `locked_until` (120 с),
    отдельная колонка вместо служебного поля `error` (иначе служебные данные
    утекали бы в публичный API).
13. Аренда в поле `error` смешивалась с текстом ошибки → выделена колонка
    `locked_until` и миграция.
14. Вызов MCP-инструмента как `request` самому себе нарушал запрет
    self-message → такие вызовы отправляются как `event`.
15. Пустая тема автоматически создаваемого диалога делала список диалогов
    бесполезным → тема формируется как «Отправитель → Получатель».
16. `greenlet` не объявлен в зависимостях: SQLAlchemy async использует его в
    рантайме, локально он стоял транзитивно, а в чистом окружении CI
    `alembic upgrade head` падал (`ModuleNotFoundError`) и все тесты падали
    на setup → добавлен в `dependencies`, conftest подсказывает причину.

### Дефекты, найденные при реализации этапа 4

17. `plan_events.actor` был `VARCHAR(40)`, а значение `user:<uuid>` длиннее →
    `StringDataRightTruncationError` на первом же событии; расширено до 120.
18. Результаты зависимостей терялись: `sync_plan` перезаписывал
    `step.output_payload` результатом задачи, и вход следующего шага не
    содержал данных предшественника → введено отдельное поле
    `resolved_input` (снимок того, что реально получил исполнитель).
19. `sync_plan` менял статусы, но не пересчитывал готовность → шаги
    оставались `pending` и не запускались; `_refresh_readiness` вызывается
    внутри синхронизации.
20. Тест «неизвестная возможность» выявил слишком строгую проверку: реестр
    разрешает объявлять новые возможности, а план требовал наличия в
    таксономии → проверяется формат ключа, а отсутствие исполнителя
    выражается состоянием шага `blocked`.
21. `retry_step` отклонял повтор, если шаг ещё не синхронизирован с задачей
    (`step_not_retryable`) → повтор сначала вызывает `sync_plan`.
22. Фикстура `session` закрывала соединения asyncpg в другом event loop
    (`attached to a different loop`) — тесты проходили, но teardown падал;
    включён `asyncio_default_test_loop_scope = "session"`.

## Известные ограничения этапа 3

* доставка **at-least-once**, не exactly-once: получатель должен быть
  идемпотентным по `message_id`/`idempotency_key` (ADR-0006);
* MCP поддерживает HTTP-транспорт (JSON-RPC); `stdio` требует адаптера на
  стороне узла;
* синхронизация инструментов MCP фиксируется как запрос — сам `tools/list`
  выполняет воркер (backend не делает исходящих вызовов к недоверенным серверам);
* push-уведомления узлам о новых заданиях не реализованы (узлы опрашивают
  очередь), Redis недоступен в dev-окружении — WebSocket-события между
  репликами не проверены живьём;
* события диалога публикуются в шину без гарантии доставки: источник истины —
  сообщения в БД.

## Известные ограничения этапа 4

* продвижение плана требует вызова `POST /plans/{id}/run` — фонового
  диспетчера нет (сознательно: не усложняем развёртывание, ADR-0007);
* условные переходы и циклы не поддерживаются — только DAG и политика отказа;
* результаты шагов хранятся в JSONB; для крупных артефактов нужен внешний
  storage;
* декомпозиция агента применяется только после явного `adopt`;
* `max_parallelism` ограничен сверху 16.
