## Осознанные ограничения (известные и задокументированные)

1. **Sandbox `subprocess` не блокирует сеть на уровне ядра.** Это dev/testing
   раннер. Для production предусмотрен `docker` (`--network none`, read-only,
   cap-drop). Ограничение зафиксировано в ADR-0003 и SECURITY.md.
2. **Anti-replay деградирует без Redis (fail-open).** Подпись и временное окно
   проверяются всегда; при недоступности Redis инцидент логируется. Выбор в
   пользу доступности, см. ADR-0002.
3. **Репутация сглаженная** (`PRIOR = 2.5`, вклады с весами) — см. этап 5 и
   ADR-0008; используется как порог допуска к наградам и как вес скоринга.
4. **Уведомление узла о новой задаче — poll-модель** (по умолчанию 2 с).
   Push-уведомление через Pub/Sub запланировано на этап 3.
5. **Нет подтверждения email и восстановления пароля** — этап 1 в scope не
   включал, но для публичного запуска нужно.
6. **Экономика внутренняя** — единицы ACU не деньги и не криптовалюта:
   нет внешних платежей, вывода в реальные средства, мультивалютности,
   версионирования правил наград. Один процессор — PostgreSQL.
7. **Нагрузочное тестирование, бэкапы, независимый аудит** — этап 9.

### Дефекты, найденные тестами и исправленные

1. Route ordering: `/nodes/{node_id}` перехватывал `/nodes/me` → выделен
   отдельный роутер с приоритетным подключением.
2. Anti-replay: `consume_once` возвращал `True` и при «Redis недоступен», и при
   успешном `SET NX` → введён сентинел `UNAVAILABLE`, replay теперь отсекается.
3. Отзыв сессий при replay откатывался вместе с ошибкой аутентификации →
   защитная мера фиксируется отдельной транзакцией.
4. Heartbeat: `sequence` от клиента вызывал конфликт уникальности → последовательность
   назначает сервер, клиентское значение сохраняется в `details`.
5. Устаревшие коллекции после изменения возможностей (identity map) → `populate_existing`.
6. `updated_at` с server-side `onupdate` вызывал `MissingGreenlet` при сериализации
   → вычисляется в Python.
7. Инъекция `ValueError` в тело ответа валидации ломала сериализацию → `jsonable_encoder`.
8. Удаление агента с версиями падало на `NOT NULL agent_versions.agent_id`
   (ORM обнулял FK вместо каскада) → `passive_deletes=True` + регресс-тест.
9. Удаление агента с историей заданий делало историю сиротой → возвращается
   `409 agent_has_tasks`, предлагается архивирование + тест.
10. Маршрут `/messages/stats` перехватывался `/messages/{message_id}`
    (`stats` парсился как UUID → 422/401) → статический маршрут объявлен выше
    динамического + параметризованный тест.
11. `ConversationDetail` читал ленивую связь `messages` при `lazy='raise'`
    → сериализация падала; детали диалога собираются из явного запроса истории.
12. Повторный `claim` возвращал то же сообщение дважды (статус `processing`
    попадал в выборку) → введена аренда доставки `locked_until` (120 с),
    отдельная колонка вместо служебного поля `error` (иначе служебные данные
    утекали бы в публичный API).
13. Аренда в поле `error` смешивалась с текстом ошибки → выделена колонка
    `locked_until` и миграция.
14. Вызов MCP-инструмента как `request` самому себе нарушал запрет
    self-message → такие вызовы отправляются как `event`.
15. Пустая тема автоматически создаваемого диалога делала список диалогов
    бесполезным → тема формируется как «Отправитель → Получатель».
16. `greenlet` не объявлен в зависимостях: SQLAlchemy async использует его в
    рантайме, локально он стоял транзитивно, а в чистом окружении CI
    `alembic upgrade head` падал (`ModuleNotFoundError`) и все тесты падали
    на setup → добавлен в `dependencies`, conftest подсказывает причину.

### Дефекты, найденные при реализации этапа 4

17. `plan_events.actor` был `VARCHAR(40)`, а значение `user:<uuid>` длиннее →
    `StringDataRightTruncationError` на первом же событии; расширено до 120.
18. Результаты зависимостей терялись: `sync_plan` перезаписывал
    `step.output_payload` результатом задачи, и вход следующего шага не
    содержал данных предшественника → введено отдельное поле
    `resolved_input` (снимок того, что реально получил исполнитель).
19. `sync_plan` менял статусы, но не пересчитывал готовность → шаги
    оставались `pending` и не запускались; `_refresh_readiness` вызывается
    внутри синхронизации.
20. Тест «неизвестная возможность» выявил слишком строгую проверку: реестр
    разрешает объявлять новые возможности, а план требовал наличия в
    таксономии → проверяется формат ключа, а отсутствие исполнителя
    выражается состоянием шага `blocked`.
21. `retry_step` отклонял повтор, если шаг ещё не синхронизирован с задачей
    (`step_not_retryable`) → повтор сначала вызывает `sync_plan`.
22. Фикстура `session` закрывала соединения asyncpg в другом event loop
    (`attached to a different loop`) — тесты проходили, но teardown падал;
    включён `asyncio_default_test_loop_scope = "session"`.

## Известные ограничения этапа 3

* доставка **at-least-once**, не exactly-once: получатель должен быть
  идемпотентным по `message_id`/`idempotency_key` (ADR-0006);
* MCP поддерживает HTTP-транспорт (JSON-RPC); `stdio` требует адаптера на
  стороне узла;
* синхронизация инструментов MCP фиксируется как запрос — сам `tools/list`
  выполняет воркер (backend не делает исходящих вызовов к недоверенным серверам);
* push-уведомления узлам о новых заданиях не реализованы (узлы опрашивают
  очередь), Redis недоступен в dev-окружении — WebSocket-события между
  репликами не проверены живьём;
* события диалога публикуются в шину без гарантии доставки: источник истины —
  сообщения в БД.

### Дефекты, найденные при реализации этапа 5

23. Мутация без `commit` в API-слое: проверки, вердикты, отзывы и апелляции
    существовали только до конца запроса — `GET /tasks/{id}/verdict` отдавал
    404 сразу после успешной проверки. Тест «вердикт после проверки» поймал
    это до релиза; во все изменяющие эндпоинты добавлен явный `commit`.
24. `ReputationBreakdown(**data, events=...)` падал с
    `TypeError: multiple values for keyword argument 'events'` — ключ уже был
    в словаре; сериализация вынесена в helper с явным сбором словаря.
25. Обращение к несуществующим полям `AgentCapability.key` / `.name` (в модели
    это `capability_key`) — 500 на `/agents/{id}/trust`; используем реальные
    колонки.
26. Проверка независимости верификатора выполнялась после проверки типа точки
    входа, поэтому при «своём» верификаторе возвращался неверный код
    `verifier_not_supported` вместо `verifier_not_independent`. Порядок
    проверок исправлен: сначала независимость, потом техническая
    поддерживаемость.
27. Формула репутации расходилась с документацией: асимметричный приор давал
    новому агенту 33.3 вместо нейтральных 50 и ломал существующий
    интеграционный тест (`reputation_score > 50` после первого успеха).
    Введён симметричный приор `PRIOR = 2.5`, ожидания зафиксированы юнит-тестами.
28. Dunder-пути в утверждениях (`a.__class__`) проходили проверку формата:
    доступ к атрибутам запрещён явно, добавлен регресс-тест на три варианта.

## Известные ограничения этапа 4

* продвижение плана требует вызова `POST /plans/{id}/run` — фонового
  диспетчера нет (сознательно: не усложняем развёртывание, ADR-0007);
* условные переходы и циклы не поддерживаются — только DAG и политика отказа;
* результаты шагов хранятся в JSONB; для крупных артефактов нужен внешний
  storage;
* декомпозиция агента применяется только после явного `adopt`;
* `max_parallelism` ограничен сверху 16.

## Известные ограничения этапа 5

* независимая проверка (`peer_agent`) поддерживает только python-агентов:
  для внешних HTTP-верификаторов нужен отдельный контракт (этап 8);
* `cross_check` (сравнение результатов двух исполнителей) объявлен в
  перечислении способов, но логики нет — вердикт по нему не выносится;
* детектор аномалий — SQL-эвристики (порог 150 мс, доля отказов > 50% при
  ≥ 8 заданиях, окно 200 заданий); сезонность и обучение не учитываются,
  ложные срабатывания снимаются админом вручную;
* репутация пересчитывается в Python после каждого вклада: при десятках
  тысяч событий на агента потребуется инкрементальный кэш (этап 9);
* проверка JSON-схемы — собственное подмножество (`type`, `required`,
  `properties`, `items`, `minimum/maximum`, `minLength/maxLength`, `enum`),
  без `$ref`, `oneOf`, `pattern` и вложенных `additionalProperties`;
* вердикт выносится по завершённым проверкам; незавершённая (`pending`,
  `running`) не блокирует вердикт, а просто не учитывается;
* репутация не влияет на допуск к заданиям напрямую — только через
  ранжирование при подборе исполнителя (0.2 веса в скоринге).

### Дефекты, найденные при реализации этапа 6

29. Счета, создаваемые лениво внутри `GET /economy/me` и `GET /economy/accounts`,
    не сохранялись: транзакция откатывалась при завершении запроса, и следующие
    запросы создавали счёт заново с нулевым балансом (в живом прогоне
    `POST /tasks` падал с `insufficient_funds`, хотя `GET /economy/me` показывал
    баланс). В оба обработчика добавлен явный `commit`.
30. Награда начислялась только в момент расчёта по бюджету, поэтому проверка,
    пришедшая после расчёта, давала 0 наград. Начисление перенесено в момент
    вердикта (ленивый импорт `economy_service.grant_reward`), идемпотентность
    держится на уникальности `(agent_id, task_id)`.
31. `scripts/seed_demo.py` создавал пользователя с ролью `developer`, из-за чего
    казна не попадала в его список счетов и пополнение молча пропускалось.
    Роли намеренно нельзя выдать через API, поэтому добавлено явное
    `promote_to_admin` (прямое обновление роли в БД) и повторный вход для
    обновления claims.
32. Повторный запуск seed падал на `409 node_name_taken` (внутри ветки ошибки
    стоял `return 0`) — теперь используются сохранённые учётные данные узла из
    `var/seed-node-credentials.json`.

## Известные ограничения этапа 6

* единицы ACU — внутренний учёт: нет внешних платежей, вывода в деньги,
  мультивалютности и KYC;
* горячие счета (казна, популярный агент) сериализуются на блокировках
  PostgreSQL; при росте нагрузки нужны партиционирование проводок и
  агрегированные счета-буферы (этап 9);
* инвариант «кэш счёта = сумма проводок» поддерживается сервисом, а не
  ограничением БД; расхождение обнаруживается `POST /economy/verify`, но не
  предотвращается;
* ставки наград меняются админом без версионирования правил: в начислениях
  хранится снимок состава (`base + bonus`), но не снимок всего правила;
* `cost_units` сообщает узел; он ограничен бюджетом сверху, но не проверяется
  на «честность» — фактическая стоимость работы не измеряется отдельно;
* награда привязана к вердикту `verified`; повторная проверка с другим
  вердиктом уже начисленную награду не отзывает (только обратная транзакция
  админом).

### Дефекты, найденные при реализации этапа 8

33. Два разных потолка лимитов: схема версии разрешала `max_wall_seconds` до
    7200, а проверка совместимости считала пределом 600 и отклоняла валидные
    версии. Пределы сведены к одному источнику (`ResourceLimits`), совпадение
    закреплено тестом, который читает метаданные полей Pydantic.
34. `budget_units` принимался при постановке задания, но отсутствовал в
    `TaskPublic` — клиент не мог подтвердить, что бюджет заморожен (в e2e это
    проявилось как `KeyError: 'budget_units'`).
35. Негативный прогон проверки совместимости записывался как «последняя
    проверка» и делал готового агента «неготовым» в портале. Введён флаг
    `is_negative`: он проверяет валидатор, а не агента, и не влияет на
    готовность.
36. Шаблоны существовали только как константы в коде, поэтому `/developer/portal`
    на свежей базе показывал «0 шаблонов». Загрузка шаблонов в БД сделана
    идемпотентной и вызывается из API портала, списка шаблонов и статистики.

## Известные ограничения этапа 8

* проверка совместимости исполняет python-агента в песочнице `subprocess`:
  сеть не блокируется на уровне ядра (ADR-0003), для недоверенного кода нужен
  `docker`-раннер;
* `http`/`docker`/`mcp`-агенты проверяются статически: реальное исполнение
  видно только через задание на узле;
* проверка доступности интеграции — один `GET` без повторов и без проверки
  содержимого: «живо» не значит «отвечает по контракту»;
* каталог интеграций — описание, а не прокси: вызовы выполняет агент со
  своего узла, платформа секретов не хранит и исходящих вызовов по манифесту
  не делает;
* SDK покрывает Python; для других языков — генерация клиента из
  `/openapi.json`, готовых пакетов нет;
* версионирования шаблонов нет: обновление меняет шаблон для всех, счётчик
  `downloads` условен (увеличивается при каждом чтении карточки).

### Дефекты, найденные при реализации этапа 9

37. **Блокирующий event loop в аутентификации.** Нагрузочный тест показал вход
    на 15 rps при p95 4,6 с и 40 параллельных клиентах: `hashlib.pbkdf2_hmac`
    (260 000 раундов) выполнялся прямо в event loop и сериализовал все
    запросы. Вынесен в выделенный пул потоков (`min(64, cpu*4)`) — 28 rps,
    p95 1,15 с; дальше упор уже в процессор, а не в планировщик.
38. **Обход проверки прав в `/ops/*`.** Хелпер `require_admin` — это
    async-зависимость FastAPI; вызов `require_admin(user)` внутри обработчика
    без `await` создавал корутину и молча ничего не проверял, то есть health,
    метрики, обслуживание и **бэкап данных** были доступны любому
    авторизованному участнику. Тест «403 для обычного пользователя» поймал
    это до релиза; обработчики переведены на зависимость `AdminUser`.
39. **Метки метрик содержали идентификаторы.** `_route_template` ожидал
    `request.scope["route"]`, но маршрутизация выполняется внутри стека
    middleware, поэтому в `scope` его ещё нет — метка становилась фактическим
    URL с UUID. Добавлена нормализация пути (UUID / длинные hex / числа →
    плейсхолдеры), тест проверяет отсутствие идентификатора в выдаче.
40. `collect_gauges` обращался к несуществующей колонке
    `InfrastructureNode.last_heartbeat_at` (в модели `last_seen_at`) — метрика
    мёртвых узлов падала на первом же scrape. Исправлено, добавлен тест.
41. Демон обслуживания, запущенный при разборе, пометил offline тестовый узел
    (его воркер не был запущен), после чего `e2e_economy` не смог получить
    задание. Это **корректное** поведение защиты от мёртвых узлов: сценарий
    требует живого воркера; последовательность «seed → e2e» восстановлена.

## Известные ограничения этапа 9

* gauge'и считаются запросами при каждом scrape: при частом scrape нужен кеш
  на 5–10 с или отдельный экспортёр;
* счётчики метрик живут в памяти процесса и обнуляются при рестарте (для
  `rate()` в Prometheus это норма, «всего за всё время» посчитать нельзя);
* `/ops/backup` — логический снимок без межтабличной согласованности, **не**
  замена `pg_dump`/PITR; восстановление требует ручной сборки, автоматической
  проверки восстановления нет;
* нагрузочные цифры получены на одном процессе API с локальной БД
  (2 ядра): чтение каталога 115–126 rps при p95 340–480 мс, смешанный профиль
  108 rps, вход 28 rps; горизонтальное масштабирование API не измерялось
  (нет балансировщика в песочнице);
* партиционирование `ledger_entries`, `task_events`, `agent_messages` не
  сделано — план на рост данных, а не текущая потребность;
* rate-limit считается по IP: клиенты за одним NAT делят 240/мин, лимита по
  токену нет;
* независимый аудит безопасности и пентест — внешняя задача, этап не закрывает;
* алертинга нет: есть метрики и предупреждения, но не правила оповещения
  (Alertmanager) и не дежурные ротации.
