# Нагрузка и chaos: что измерено (этап 10, H)

Документ фиксирует **фактические замеры** и параметры, при которых они
получены. Правило: если сценарий не удалось выполнить, он помечается
`skipped` с причиной — «не проверяли» здесь не превращается в «проверено».

Воспроизведение: `backend/scripts/bench_report.py` (обёртка) +
`backend/scripts/load_test.py` (сам нагрузчик). Отчёт пишется в JSON: там
все параметры, ресурсы и вердикт по каждому сценарию.

```bash
# 1. база и зависимости
export DATABASE_URL="$(cat /tmp/pguri)"          # Postgres 16 (pgserver)
python scripts/dev_redis.py --port 6379 &        # fakeredis по TCP

# 2. API (один процесс, как в замерах)
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1

# 3. замер
BENCH_ADMIN_EMAIL=... BENCH_ADMIN_PASSWORD=... \
INTERNAL_SERVICE_TOKEN=... WORKER_LEASE_SECONDS=8 \
python scripts/bench_report.py --scenarios read mixed auth \
    --requests 120 --concurrency 10 --chaos --label final-2vcpu \
    --out bench.json
```

## 1. Условия замера

| Параметр | Значение |
|---|---|
| Дата | 2026-11-06 |
| CPU | 2 vCPU (общая песочница, `nproc` = 2) |
| RAM | 3.9 GiB, RSS процесса API после прогона 131.6 MB |
| API | 1 процесс uvicorn, 1 воркер, `ENVIRONMENT=development` |
| Python | 3.11.2 |
| БД | локальный Postgres 16 (`pgserver`), пул 10 + 20 overflow |
| Redis | `fakeredis` по TCP (`scripts/dev_redis.py`), не redis-server |
| Нагрузка | 120 запросов на профиль, конкурентность 10 |
| Лимиты в замере | подняты (`auth` 600/мин, `default` 3000/мин), иначе профиль измеряет лимит, а не систему |
| Аренда | `WORKER_LEASE_SECONDS=8` (чтобы chaos-окно возврата было коротким) |

Чего эти цифры **не** описывают: горизонтальное масштабирование (нет
балансировщика), поведение на реальном Redis, работу под нагрузкой с
диском БД на отдельном хосте, `docker`-песочницу (в замере `subprocess`).

## 2. Производительность

| Профиль | Что делает | RPS | p50 / p95 / p99 | Ошибки | CPU (доля ядра) |
|---|---|---|---|---|---|
| `read` | `GET /agents` с фильтрами | 85.6 | 113 / 188 / 205 мс | 0 | 75 % |
| `mixed` | 80 % чтений + 20 % постановки заданий | 76.3 | 128 / 203 / 241 мс | 0 | 74 % |
| `auth` | вход (PBKDF2 260 000 раундов) | 21.5 | 459 / 583 / 702 мс | 0 | 152 % |

Наблюдения, которые важны для эксплуатации:

* **Чтение упирается в CPU процесса, а не в БД** — при 2 ядрах один
  воркер занимает ~75 % ядра на 85 rps. Масштабирование — реплики API.
* **Вход — на порядок дороже чтения** (в 6 раз меньше rps при 2× CPU):
  стоимость PBKDF2 неизбежна, поэтому вход ограничен rate-limit'ом
  (20/мин на IP по умолчанию) и вынесен в пул потоков ещё на этапе 9.
* p95 `auth` 583 мс против 188 мс у чтения — это разница между «посчитать
  хеш» и «прочитать строку»; порог алерта для `auth` должен быть своим.

Предыдущий базовый замер (этап 9, тот же класс машины): чтение 115–126 rps
p95 340–480 мс, вход 28 rps p95 1.1 с. Цифры отличаются, потому что
изменились и код (этапы 10 A–G: аудит, лимиты, метрики), и профиль
(120 запросов вместо 200, другая конкурентность). Сравнивать их напрямую
нельзя — это разные прогоны, а не «ускорение».

## 3. Chaos-сценарии

| Сценарий | Как воспроизведён | Наблюдаемый результат | Вердикт |
|---|---|---|---|
| `redis-down` | Redis не запущен; вход неизвестным email + узел | 0 ответов 5xx; лимиты работают локально; подписанные запросы узла отклоняются `replay_protection_unavailable` (fail-closed) | ✅ |
| `redis-flap` | Redis работает, 20 параллельных чтений | 0 ответов 5xx | ✅ |
| `worker-killed` | узел забирает задание (HMAC), «умирает»; ждём истечения аренды; проход обслуживания | аренда взята (`assignments=1`), `stuck_leases=1`, через 10.1 с аренда истекла, `requeued_tasks=1`, задание снова `queued` | ✅ |
| `db-pool-exhausted` | 40 параллельных запросов при пуле 10+20 | 40×200, 0 ответов 5xx, 0.69 с — пул ждёт, а не отдаёт ошибку | ✅ |

Важно про `worker-killed`: сценарий измерим только при доступном Redis —
anti-replay подписей узлов работает fail-closed, и без Redis claim честно
отклоняется. Поэтому в замере поднят `fakeredis` по TCP. Это не
redis-server: проверяется логика приложения, а не производительность Redis.

## 4. Дефекты, найденные chaos-тестом

Нагрузка и отказы нашли два дефекта, которые не видны в обычных тестах:

1. **Просроченные задания залипали в очереди навсегда.** `deadline_at`
   проверялся только при выдаче задания узлу. Если подходящего узла нет,
   задание оставалось `queued` вечно: очередь росла, бюджет оставался
   замороженным, отменить его мог только автор.
   Исправлено: `gateway.expire_overdue_tasks`, вызывается обслуживанием и
   `POST /ops/maintenance`; бюджет возвращается, событие `task.expired`
   пишется с актором `maintenance`.
   Регрессия: `tests/api/test_overdue_tasks.py`.

2. **Просроченные задания «съедали» окно выдачи.** Окно кандидатов
   (`limit * 4`) заполнялось мёртвыми заданиями, они закрывались внутри
   цикла, и выдача возвращала пустой список при живой очереди ниже — узел
   простаивал. Исправлено фильтром по дедлайну в SQL.
   Регрессия: `test_claim_does_not_starve_behind_expired_tasks`.

## 5. Метрики, добавленные под эти замеры

| Метрика | Тип | Зачем |
|---|---|---|
| `task_duration_ms` | гистограмма | от создания до финального статуса: видит и ожидание в очереди |
| `task_execution_ms` | гистограмма | от аренды до ответа узла: деградация агента отдельно от очереди |
| `task_outcome{outcome}` | счётчик | succeeded / failed / retry |
| `task_expired_in_queue` | счётчик | задания, закрытые по дедлайну до выдачи |
| `mcp_call` / `mcp_error{outcome}` + `mcp_tool_call` | счётчик + гистограмма | отказы MCP по типу, без токена в метке |
| `db_pool_checked_out`, `db_pool_overflow`, `db_pool_utilization`, `db_pool_available` | gauge | утечка соединений и нехватка пула |
| `worker_<name>_age_seconds` | gauge | возраст последнего прохода (`maintenance`, `outbox`, `backup`, `message_worker`) |
| `worker_pass_failed{outcome}` | счётчик | проход воркера упал (БД/инфраструктура) |
| `ratelimit_hit_redis` / `_local`, `ratelimit_backend_fallback` | счётчик | видно, что Redis деградировал |

`/ops/health` отдаёт `worker_stalled` при возрасте > 300 с и блок `config`
с фактическими лимитами, пулом и интервалами воркеров — числа из этого
документа можно сверить с работающим процессом, не читая `.env`.

## 6. Что нужно для честного «production»-замера

1. Отдельный хост для БД и реальный Redis (а не `fakeredis`).
2. Балансировщик и ≥ 2 реплики API: без этого горизонтальное
   масштабирование не измеряется.
3. Драйвер нагрузки вне измеряемого хоста: сейчас клиент и сервер делят
   2 vCPU, поэтому rps занижен, а p95 завышен.
4. Профиль с записью на уровне «много заданий и много узлов»: текущий
   `mixed` создаёт 20 % заданий и не проверяет насыщение узлов.
5. Прогон длиннее 10 минут: короткий профиль не показывает рост памяти и
   деградацию пула.
