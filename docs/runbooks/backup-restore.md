# Runbook: резервное копирование и восстановление

Документ отвечает на вопрос «что делать», а не «что настроено». Все цифры
ниже — либо требование, либо **замер** (тогда указано, чем измерено).

## 1. Что считается бэкапом

| Слой | Что даёт | Кто делает | Проверено |
|---|---|---|---|
| Физический `pg_basebackup` + WAL-архив | восстановление на момент времени (PITR), транзакционная согласованность | инфраструктура (см. §5) | процедура описана, в этом репозитории не автоматизирована — **честно: не проверено нами** |
| Логический снимок `POST /ops/backups` | проверка целостности данных, перенос между средами, «человекочитаемая» копия | сервис (`app/services/backup.py`) | **проверено**: `tests/api/test_backup_restore.py` делает реальное восстановление |
| Аудит-лог | разбор инцидентов (кто и что менял) | сервис | проверено тестами API |

Логический снимок **не заменяет** PITR: он читает таблицы отдельными
запросами и не даёт транзакционной согласованности между ними. В коде это
написано прямым текстом, чтобы никто не принял его за полноценный бэкап.

## 2. Как выглядит снимок

```
var/backups/ac-20261106T063004-4b2b08e75a0e.acbk       # ACBK1 + версия ключа + nonce + AES-256-GCM
var/backups/ac-20261106T063004-4b2b08e75a0e.acbk.json  # манифест: таблицы, число строк, checksum
```

* шифрование: AES-256-GCM, ключ выводится из `BACKUP_ENCRYPTION_KEY`
  (отдельный от `SECRET_KEY`), контекст `agent-civilization:backup:v1`;
* версия ключа входит в контейнер → ротация ключей не ломает старые бэкапы;
* манифест позволяет проверить целостность до восстановления.

## 3. Создание

```bash
# разово (админ)
curl -X POST https://api.example.com/api/v1/ops/backups -H "Authorization: Bearer $ADMIN"

# автоматически (демон; в docker-compose сервис `backup`)
python -m app.worker.backup --interval 3600
```

Демон после создания **сразу проверяет бэкап восстановлением** и пишет
`backup_verify` в метрики: зелёный CI не означает «бэкап рабочий».

## 4. Восстановление (проверка)

```bash
curl -X POST https://api.example.com/api/v1/ops/backups/<file>/verify -H "Authorization: Bearer $ADMIN"
```

Ответ:

```json
{
  "ok": true,
  "schema": "restore_1793946564",
  "rows_expected": 328,
  "rows_restored": 328,
  "unbalanced_transactions": 0,
  "checksum_plain": "…"
}
```

Данные вставляются в схему `restore_<timestamp>`: рабочая схема не
затрагивается. `ok=false` означает, что бэкап повреждён или потерял строки —
использовать его нельзя.

Перенос в рабочую схему — **отдельное осознанное действие оператора**
(не автоматизировано намеренно: необратимые операции не должны выполняться
одной командой API).

## 5. Production: физический бэкап (внешний слой)

Требуется от инфраструктуры (managed Postgres или собственный кластер):

1. `archive_mode = on`, `archive_command` в объектное хранилище;
2. `pg_basebackup` ежедневно, хранение ≥ 30 дней;
3. хранилище бэкапов — **отдельный аккаунт/бакет**, без доступа из
   приложения к продакшн-базе;
4. шифрование на стороне хранилища + собственная копия ключа вне кластера;
5. раз в неделю — автоматический прогон восстановления в чистую среду.

Пункты 1–5 — требования к платформе; в этом репозитории их нельзя
«включить». В отчёте они отмечены как **требуют инфраструктуры**, а не как
«сделано».

## 6. RPO / RTO

| Показатель | Значение | Комментарий |
|---|---|---|
| RPO (логический снимок) | `BACKUP_INTERVAL_SECONDS` (по умолчанию 3600 с) | потеря — до одного интервала |
| RPO (PITR) | ≤ 5 минут (зависит от `archive_timeout`) | требует настройки кластера |
| RTO (проверка бэкапа) | секунды–минуты на объёме до 10⁵ строк | замерено тестом `test_backup_worker_passes_and_verifies` |
| RTO (полное восстановление сервиса) | `RTO_TARGET_SECONDS` = 1800 с | цель; **не замерялась на production-объёме** |

Правило: RTO/RPO — цель, пока нет замера на реальном объёме. В отчёте так и
записано.

## 7. Retention

`BACKUP_KEEP_DAYS` (по умолчанию 14). Удаление делает демон: файл и
манифест удаляются вместе, «сирот» не остаётся.

## 8. Ответственные

| Роль | Ответственность |
|---|---|
| Владелец сервиса | политика хранения, проверка отчётов `backup_verify` |
| Дежурный инженер | реакция на `backup_verify_failed`, ручной прогон восстановления |
| Платформенная команда | `pg_basebackup`, WAL-архив, отдельное хранилище |

Роли не автоматизируются: их наличие — организационное требование.

## 9. Диагностика

| Симптом | Причина | Действие |
|---|---|---|
| `backup_verify_failed` | данные изменились между снимком и манифестом, повреждён носитель | создать новый снимок, проверить диск/хранилище |
| `Не удалось расшифровать бэкап` | сменился `BACKUP_ENCRYPTION_KEY` и старая версия удалена из кольца | вернуть версию ключа в `SECRET_ENCRYPTION_KEYS`-кольцо бэкапов |
| `Неверный формат контейнера` | файл не `.acbk` или обрезан | использовать другой снимок, проверить размер |
| `cannot execute ... in a read-only transaction` | снимок выполнялся в чужой транзакции | использовать API/демон (они открывают своё соединение) |
