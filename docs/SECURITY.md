# Модель безопасности

## 1. Аутентификация пользователей

| Механизм | Реализация |
|---|---|
| Хранение паролей | PBKDF2-HMAC-SHA256, 260 000 итераций, случайная соль 16 байт; параметры хранятся в хеше, при повышении стоимости пароль пере-хешируется при входе |
| Access-токен | JWT HS256, TTL 15 мин, тип `access` обязателен |
| Refresh-токен | JWT HS256, TTL 30 дней, серверная сессия в БД (`refresh_token_sessions`) |
| Ротация refresh | каждый обмен выдаёт новую пару; старый токен помечается использованным |
| Детект компрометации | повторное использование отозванного refresh-токена отзывает **все** сессии пользователя (транзакция фиксируется отдельно, чтобы откат ошибки не отменил защиту) |
| Смена пароля | отзывает все сессии |
| Выход | отзыв одной или всех сессий |
| Тайминг-атаки | при неизвестном email выполняется проверка фиктивного хеша, ответ неотличим от неверного пароля |

## 2. Авторизация

* Роли: `member`, `developer`, `admin`.
* Проверка владельца — на каждом изменяющем эндпоинте агентов, узлов и задач.
* Черновики и архивные агенты не видны посторонним: возвращается `404`, а не
  `403`, чтобы не раскрывать существование ресурса.
* Внутренний `entrypoint_config` (с секретами внешнего сервиса) доступен только
  владельцу и админу; наружу отдаётся отфильтрованная версия без ключей
  `api_key`, `token`, `secret`, `password`, `headers`, `code` и др.
* Журнал аудита: не-админ видит только свои записи, параметр `all_entries`
  игнорируется для не-админов.
* Экономика: счёт доступен только владельцу, казна — только админу; чужой
  перевод, списание и отмена операции → `403`. Баланс нельзя изменить напрямую
  через API: единственный путь — сбалансированная транзакция с двумя и более
  проводками, а пополнение возможно только переводом из казны (никакого
  «создания» единиц). Стартовый грант, заморозка бюджета и награды
  идемпотентны по уникальному ключу операции, поэтому повтор запроса или
  повторный отчёт узла не задваивает выплату. Правила наград меняет только
  админ (с записью в аудит).

## 3. Аутентификация инфраструктурных узлов

Пароли для машин не используются. Узел подписывает каждый запрос:

```
key       = sha256(node_secret)          # хранится на сервере
signature = HMAC-SHA256(key, canonical)  # canonical = key\nmethod\npath\ntimestamp\nnonce\nsha256(body)
```

* Сервер **не хранит** `node_secret` — только хеш, поэтому утечка БД не даёт
  возможности подписывать запросы от имени узла.
* `timestamp` проверяется с допуском ±60 секунд (`NODE_REQUEST_MAX_SKEW_SECONDS`).
* `nonce` запоминается в Redis на время двойного окна; повтор → `replay_detected`.
  При недоступности Redis защита деградирует (fail-open) с записью инцидента в лог —
  это осознанный выбор в пользу доступности; подпись и окно времени продолжают работать.
* Подпись привязана к методу, пути и телу запроса: изменение любого из них
  инвалидирует подпись.
* Ротация секрета переводит узел в `pending` до нового подтверждения.
* Отозванный узел (`revoked`) не может ни читать, ни получать задания.

## 4. Исполнение недоверенного кода

Правило №7 роадмапа соблюдается строго: код агентов **не исполняется**
в процессе backend.

`subprocess` (dev/тесты):
* отдельный процесс, чистый `env` (без `SECRET_KEY`, `DATABASE_URL` и т.п.);
* `RLIMIT_CPU`, `RLIMIT_AS`, `RLIMIT_NOFILE`, `RLIMIT_NPROC`;
* wall-clock таймаут с принудительным kill;
* ограничение размера stdout/stderr;
* изолированный временный рабочий каталог, удаляемый после запуска.

`docker` (production, рекомендуется):
* `--network none` по умолчанию, `--read-only`, `--cap-drop ALL`,
  `--security-opt no-new-privileges`, `--user 65534`;
* лимиты `--memory`, `--memory-swap`, `--cpus`, `--pids-limit`;
* тот же wall-clock таймаут и очистка каталога.

Ограничения песочницы `subprocess`: сетевой доступ не блокируется средствами
ядра — для production используйте `docker` (см. `docs/STATUS.md`).

## 5. Транспорт и заголовки

* CORS с явным списком источников (`CORS_ORIGINS`), credentials разрешены.
* Security-заголовки: `X-Content-Type-Options`, `X-Frame-Options: DENY`,
  `Referrer-Policy`, HSTS в production.
* `X-Request-ID` сквозной, попадает в логи и в тело ошибки.
* Логи — JSON, без секретов и паролей.

## 6. Rate limiting

* Вёдра лимитов (`RATE_LIMIT_*_PER_MINUTE`): `default` 240/мин, `auth`
  20/мин, `write` 120/мин, `critical` 20/мин, `node` 1200/мин.
* Ключ: аккаунт, если токен валиден (смена IP не обходит лимит), иначе IP.
  IP берётся с учётом только доверенных прокси (`TRUSTED_PROXIES`).
* **Redis недоступен → лимиты не отключаются.** Счётчик переходит в память
  процесса (`ratelimit_backend_fallback_total`); при нескольких репликах
  это даёт `limit × реплики` — слабее точного общего лимита, но строго
  лучше полного отсутствия ограничения.
* **Anti-replay подписей узлов — fail-closed.** Без Redis подписанный
  запрос отклоняется (`replay_protection_unavailable`), узел повторит его.
* Подтверждение email и сброс пароля лимитируются отдельно (вход/регистрация
  — вёдро `auth`, `critical` — смена пароля и 2FA).

## 6a. Метрики и служебные эндпоинты (этап 9)

* `/metrics` закрыт сервисным токеном (`X-Service-Token`); открыть без токена
  можно только осознанно — `METRICS_PUBLIC=true` (внутри закрытого кластера).
  Метрики раскрывают нагрузку, объём данных и размеры таблиц.
* Метки метрик не содержат идентификаторов: путь нормализуется до шаблона,
  иначе каждая сущность создавала бы новую серию (кардинальность).
* `/ops/*` (health, метрики, таблицы, обслуживание, бэкап) требует роли
  `admin` через зависимость FastAPI, а не ручную проверку в теле обработчика
  (дефект 38: вызов async-хелпера без `await` не проверял ничего).
* Бэкап отдаёт только таблицы из белого списка; имя таблицы не подставляется
  из запроса напрямую (`backup_table_unknown` на всё остальное).
* Вход под паролем: 260 000 раундов PBKDF2 в выделенном пуле потоков —
  стоимость подбора не снижена, но event loop больше не блокируется
  (дефект 37), а rate-limit 20/мин на IP остаётся первой линией.

## 7. Аудит

Пишутся: регистрация, вход, выход, смена пароля, все операции с агентами,
версиями и возможностями, регистрация/ротация/отзыв/верификация узлов,
постановка и отмена задач, приём результатов, проверки и вердикты, отзывы,
апелляции, а также финансовые операции: `economy.transfer`, `economy.withdraw`,
`economy.reverse`, `economy.rule.update`. Поля: актор, действие, объект,
результат, IP, User-Agent, `request_id`, полезная нагрузка (без секретов).

## 8. Проверено тестами

`tests/security/test_access_control.py` и `tests/unit/test_security.py`:

* анонимный доступ к изменяющим операциям;
* попытки изменить чужого агента (update/publish/suspend/resume/archive/version);
* попытки управлять чужим узлом;
* подделка подписи узла, устаревший timestamp, replay с тем же nonce;
* работа отозванного узла;
* SQL-инъекции в поиске (параметризованные запросы);
* отсутствие утечек в тексте ошибок;
* правило «нельзя действовать от имени другого пользователя в журнале аудита»;
* экономика: чужой счёт, чужой перевод и чужая отмена → `403`; казна скрыта
  от не-админа; несбалансированная транзакция и транзакция из одной проводки
  отклоняются (`ledger_unbalanced`, `ledger_needs_two_entries`); повтор с тем
  же ключом идемпотентности не создаёт новой операции; повторная отмена уже
  отменённой операции → `409 transaction_already_reversed`; сверка журнала
  (`POST /economy/verify`) даёт нулевую сумму всех балансов.

## 9. Политика раскрытия уязвимостей

**Куда сообщать.** Приватный канал GitHub Security Advisory в репозитории
(«Security» → «Report a vulnerability»). Публичные issue для уязвимостей не
используются: до исправления деталь эксплойта не должна быть видна.

**Что включить в отчёт:** затронутый эндпоинт или компонент, версию/коммит,
шаги воспроизведения, оценку влияния (какие данные или действия доступны
атакующему), при наличии — PoC.

**Сроки (целевые, не SLA):**

| Этап | Срок |
|---|---|
| Подтверждение получения | 3 рабочих дня |
| Первичная оценка критичности | 7 рабочих дней |
| Критично (утечка данных, обход авторизации, кража средств) | исправление или временная мера — 14 дней |
| Высокая | 30 дней |
| Средняя/низкая | следующий плановый релиз |

**Правила обработки.** Секреты и персональные данные из отчёта копируются
только в приватный advisory; в публичном описании после исправления —
механизм и версия, без эксплойта. Кредит исследователю — по его желанию.

**Вне области:** атаки на инфраструктуру, которой нет в репозитории
(балансировщик, managed Postgres, KMS), социальная инженерия, отчёты
сканеров без воспроизведения.

## 10. Что проверяется в CI и что блокирует релиз

Job `security` в `.github/workflows/ci.yml`:

| Проверка | Инструмент | Блокирует |
|---|---|---|
| SAST | `bandit -r app -ll -ii` | любая находка HIGH |
| Зависимости | `pip-audit --strict` | известная уязвимость |
| Секреты в репозитории | regex-скан (private key, AWS, GitHub, Slack, OpenAI-ключи) | любое совпадение |
| Контейнер | `trivy` (`severity: CRITICAL`, `ignore-unfixed`) | CRITICAL |
| Security-тесты | `pytest tests/security tests/unit/test_secrets.py …` | падение |
| Отказ старта в небезопасной конфигурации | `tests/api/test_security_fixes.py` | падение |

Правило этапа 10: «зелёный CI» не достигается отключением проверки. Если
находка ложноположительная — она подавляется точечно (строка + причина в
комментарии) или чинится, а не выключается целиком.

## 11. Что останется сделать перед публичным production

Закрыто на этапе 10: подтверждение email и восстановление пароля, 2FA для
админов, ротация и версионирование секретов, шифрование бэкапов, проверка
восстановления, security-сканирование в CI, нагрузка и chaos.

Остаётся (вне кода приложения или вне объёма этапа):

1. Внешний секрет-менеджер (Vault/KMS) вместо `.env` — интерфейс
   `SecretProvider` готов, сервис не подключён.
2. Независимый аудит безопасности и пентест — внешняя задача.
3. mTLS либо подпись Ed25519 для узлов (сейчас симметричный HMAC).
4. TLS-терминация и WAF у балансировщика; HSTS уже выставляется
   приложением в production.
5. Доставка алертов (Alertmanager/PagerDuty) — метрики и пороги есть,
   маршрутизация оповещений настраивается на платформе.
6. Production-подобный нагрузочный стенд (`docs/runbooks/load-and-chaos.md`
   §6): измерено на 2 vCPU с локальной БД и `fakeredis`.
