# ADR-0011. Масштабирование, наблюдаемость и обслуживание

* Статус: принято
* Дата: 2026-11-06
* Этап: 9 «Масштабирование и распределённая инфраструктура»

## Контекст

К этапу 8 система функционально полна, но эксплуатировать её вслепую нельзя:

* истёкшие аренды задач возвращал только тест — в живом развёртывании
  «зависший» узел держал задание вечно, а бюджет оставался замороженным;
* мёртвые узлы (без heartbeat) продолжали считаться online;
* не было метрик: ни очереди, ни задержек, ни разбалансировки журнала;
* нагрузочное тестирование не проводилось, узкие места были неизвестны;
* не было резервного копирования, кроме `pg_dump` «руками».

Роадмап требует: оптимизировать PostgreSQL и Redis, масштабировать воркеры,
улучшить распределение задач, обеспечить отказоустойчивость, сделать бэкапы и
восстановление, полноценную наблюдаемость, нагрузочные тесты, проверить
устойчивость к отказам узлов и выделять микросервисы только при реальной
необходимости.

## Решение

### 1. Метрики без внешних зависимостей

Собственный реестр метрик (`app/core/metrics.py`) отдаёт формат Prometheus
text exposition 0.0.4 на `/metrics`:

* `ac_http_requests_total{method,route,status}` — трафик;
* `ac_http_request_duration_ms` — гистограмма с корзинами 5 мс … 10 с;
* `ac_events_total{event,outcome}` — события домена;
* `ac_operation_duration_ms{operation}` — длительность операций
  (обслуживание, сбор метрик, бэкап);
* `ac_<gauge>` — состояние системы из базы.

Почему не `prometheus_client`: библиотека тянет зависимость и глобальное
состояние, а нам нужны ровно счётчики, гистограмма и рендер в текст — это
~150 строк, полностью покрытых тестами.

**Ограничение кардинальности** — обязательное условие, иначе метрики
убивают Prometheus. Метка маршрута берётся из шаблона, а не из URL: UUID,
длинные hex-идентификаторы и числа заменяются плейсхолдерами. Тест проверяет,
что идентификатор агента в метках не появляется. Есть жёсткий предел числа
маршрутов (`MAX_ROUTE_KEYS`), лишние считаются отдельно.

### 2. Gauge'и считаются из базы, а не из памяти

`services/observability.collect_gauges` выполняет запросы при каждом scrape:
очередь и её возраст, застрявшие аренды, просроченные дедлайны, узлы
online/stale, очередь доставки, замороженные бюджеты, вердикты, сумма всех
балансов журнала, размеры экосистемы.

Это осознанный компромисс: при нескольких репликах API все они показывают
одно и то же состояние (иначе графики «прыгают» в зависимости от того, кто
ответил на scrape), но каждый scrape стоит несколько запросов. При росте
нагрузки это лечится кешем на 5–10 секунд или отдельным экспортёром.

### 3. `/ops/health` формулирует действие, а не число

Ответ содержит `status` (`ok`/`degraded`/`critical`), gauge'и и список
предупреждений с кодом, важностью и **готовой инструкцией**:

| Код | Важность | Условие |
|---|---|---|
| `ledger_unbalanced` | critical | сумма балансов ≠ 0 |
| `no_nodes` | critical | нет online-узлов, а очередь непуста |
| `stuck_leases` | high | есть задачи с истёкшей арендой |
| `queue_backlog` | high | старейшее задание ждёт > 300 с |
| `stale_nodes` | medium | узлы без heartbeat > 120 с |
| `compat_failures` | low | провалов совместимости втрое больше успехов |

Мысль простая: дежурный ночью читает «проверьте, что воркер возврата аренд
запущен», а не «stuck_leases = 3».

### 4. Демон обслуживания как отдельный процесс

`python -m app.worker.maintenance --interval 30` — отдельный stateless-процесс
(в `docker-compose.yml` сервис `maintenance`). За проход:

1. возвращает задачи с истёкшей арендой в очередь (или помечает `expired`,
   если попытки кончились);
2. помечает узлы без heartbeat старше порога как offline;
3. истекает недоставленные сообщения;
4. снимает gauge'и и логирует предупреждения.

Почему не задача внутри API: при N репликах API нельзя гарантировать «ровно
один проход», а Redis-блокировка отказывает именно тогда, когда нужна (Redis
недоступен, а аренды возвращать надо). Все операции идемпотентны и опираются
на `FOR UPDATE SKIP LOCKED`, поэтому демонов можно запускать сколько угодно.
Тот же проход доступен вручную: `POST /ops/maintenance` (админ) — для разбора
инцидента.

Побочный эффект, который стоит знать: демон честно помечает мёртвыми узлы,
которые давно не слали heartbeat, — включая тестовый узел, если его воркер
не запущен. Это ожидаемое поведение, а не дефект (см. e2e этапа 9).

### 5. PBKDF2 — в выделенный пул потоков

Нагрузочный тест нашёл узкое место: вход давал **15 rps** независимо от
числа клиентов, потому что `hashlib.pbkdf2_hmac` (260 000 раундов) выполнялся
в event loop и блокировал всё остальное. Перенос в пул потоков
(`run_in_executor` с размером `min(64, cpu*4)`) дал **28 rps** — теперь это
предел процессора, а не планировщика. Чтение каталога на том же железе:
115–126 rps, p95 ≈ 340–480 мс при 30–40 параллельных клиентах.

Отдельный пул, а не общий `asyncio.to_thread`: вход — единственная массово
параллельная CPU-операция, и он не должен вытеснять остальные задачи.

### 6. Индексы под конкретные запросы

Миграция `75f08bc270fd` добавляет пять индексов, каждый — под запрос из кода:

* `ix_tasks_lease_expiry` (частичный, `lease_expires_at IS NOT NULL`) —
  демон обслуживания каждые 30 с;
* `ix_tasks_deadline` (частичный) — просроченные дедлайны в метриках;
* `ix_transactions_kind_created` — сводка и история операций по типу;
* `ix_reward_grants_agent_created` — дневной лимит наград;
* `ix_compat_agent_negative_created` — «последняя проверка» в портале.

Частичные индексы выбраны там, где выборка узкая: они меньше и точнее.

### 7. Резервное копирование: логический снимок + внешний `pg_dump`

`GET /ops/backup` (админ) отдаёт gzip с JSON Lines: заголовок с составом и
датой, затем по строке на запись, с `X-Checksum-Sha256` и числом строк.
Таблицы — только из белого списка (иначе SQL-инъекция через имя таблицы).

Честная оговорка, зафиксированная и в коде, и в отчёте: **это не замена
`pg_dump`/PITR**. Транзакционной согласованности между таблицами нет (каждая
читается своим запросом). Назначение — перенос данных, проверка целостности
и «снимок для разбора». Production-бэкап: `pg_dump`/WAL-архив, вынесенный
из кластера.

### 8. Устойчивость к отказам узлов

Проверено тестами, а не декларацией:

* узел не отчитался → аренда истекает → демон возвращает задачу в очередь
  (или `expired` после исчерпания попыток);
* узел молчит > порога → offline, его аренды освобождаются;
* повторный проход обслуживания ничего не возвращает дважды (идемпотентность);
* задание с истёкшей арендой не может быть завершено старым `lease_token`
  (fencing, этап 2) — проверка остаётся в силе.

Redis по-прежнему опционален: rate-limit и anti-replay деградируют
(fail-open/fail-degraded), но аренды, очередь и экономика работают.

## Последствия

**Плюсы**

* Видно деградацию до жалоб: застой очереди, мёртвые узлы, разбалансировка
  журнала, объём данных.
* Есть ответ на «почему задания висят» без чтения кода.
* Вход перестал блокировать event loop — важное исправление, найденное
  нагрузочным тестом, а не догадкой.
* Демон обслуживания делает систему самовосстанавливающейся после падения
  узлов; его можно запускать в нескольких копиях.
* Бэкап доступен без доступа к серверу БД.

**Минусы и ограничения**

* Сбор gauge'ей стоит несколько запросов на каждый scrape; при частом scrape
  нужен кеш или отдельный экспортёр.
* Метрики живут в памяти процесса: при перезапуске счётчики обнуляются
  (для Prometheus это норма — `rate()` переживает рестарты, но «всего за
  всё время» посчитать нельзя).
* `/ops/backup` не согласован между таблицами и не заменяет `pg_dump`/PITR;
  восстановление из него требует ручной сборки.
* Нагрузочный тест — синтетический (чтение каталога, постановка задания,
  вход) и запускается на одном процессе API с in-process БД; цифры
  характеризуют код, а не конкретное железо.
* Rate-limit на вход (20/мин на IP) остаётся главным ограничителем
  брутфорса; общий лимит 240/мин на IP при большом числе клиентов за одним
  NAT может мешать — нужен лимит по токену, а не только по IP.
* Партиционирование `ledger_entries` и `task_events` не сделано: при
  десятках миллионов проводок понадобится (план — следующий шаг).
* Независимый аудит безопасности и пентест остаются внешней задачей.

## Альтернативы

* **`prometheus_client`.** Отклонено: зависимость ради ~150 строк рендера.
* **Gauge'и из памяти процесса (счётчики инкрементом).** Отклонено: при
  нескольких репликах значения расходятся, а после рестарта теряются.
* **Отдельный сервис метрик/экспортёр.** Отклонено до появления реальной
  нагрузки, которая это оправдает (ADR-0001: без преждевременных
  микросервисов).
* **Обслуживание как cron внутри API.** Отклонено: невозможно гарантировать
  однократность, а Redis-блокировка ненадёжна именно в аварии.
* **`asyncio.to_thread` для PBKDF2.** Отклонено: общий пул мал и вытесняется
  остальными задачами; выделенный пул даёт предсказуемость.
