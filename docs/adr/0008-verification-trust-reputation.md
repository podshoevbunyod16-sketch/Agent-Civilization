# ADR-0008. Верификация результатов и выводимая репутация

* Статус: принято
* Дата: 2026-11-05
* Этап: 5 «Проверка и доверие»

## Контекст

К концу этапа 4 платформа умела исполнять задания и составные планы, но
единственным сигналом качества был счётчик `completed_tasks` и
байесовская формула в `gateway._update_agent_counters`. У такого подхода
четыре изъяна:

1. **Доверие не проверяемо.** Число нельзя объяснить: непонятно, из чего
   оно сложилось и какие задания за ним стоят.
2. **Нет проверки результата.** Успешный отчёт узла (`success: true`)
   считался качественным результатом, даже если данные не соответствуют
   заявленному контракту.
3. **Нет разделения «заявлено» и «проверено».** У возможности
   (`AgentCapability`) был только `declared_level`, который заполняет
   разработчик — то есть сам себя хвалит.
4. **Нет защиты от накрутки.** Повторные отчёты, копипаст результата,
   взаимные отзывы никак не обнаруживались.

## Решение

### 1. Репутация — сумма проверяемых вкладов

Вводится журнал `reputation_events`: каждый вклад имеет источник
(`task_success`, `verification_passed`, `review`, `anomaly_penalty`,
`appeal`, …), вес источника и ссылку на объект-источник. Кэш
`agents.reputation_score` пересчитывается из журнала:

```
score = 100 * (positive + PRIOR) / (positive + negative + 2 * PRIOR),  PRIOR = 2.5
```

Симметричный приор даёт нейтральный старт 50 у нового агента и не
позволяет одному отзыву обнулить историю. Вес источника отражает степень
независимости оценки: успешное задание 1.0, независимая проверка 2.0,
провал проверки 2.5, отзыв 1.5, подтверждённая аномалия до 5.0.

**Идемпотентность.** У каждого вклада есть `dedup_key`
(`task:<id>:success`, `verdict:<id>:verified`, `review:<id>`, …) с
уникальным индексом по `(agent_id, dedup_key)`. Повторный отчёт узла или
повторный запуск проверок не накручивает рейтинг — это проверено тестами
(`test_reputation_is_idempotent_per_task`).

**Отзыв вклада, а не удаление.** Апелляция не удаляет события: она
проставляет `reversed_at`. История остаётся аудируемой, а формула
пересчитывается по неотозванным вкладам.

### 2. Проверка результата — отдельная сущность

`task_verifications` хранит одну проверку: способ, статус, вес,
идентификатор верификатора и детали. Способы:

| Способ       | Где исполняется        | Вес |
| ------------ | ---------------------- | --- |
| `schema`     | процесс API            | 1.0 |
| `assertions` | процесс API            | 1.0 |
| `auto_test`  | **песочница**          | 1.5 |
| `peer_agent` | песочница верификатора | 2.5 |
| `human`      | —                      | 3.0 |

Проверка схемы — собственная минимальная реализация подмножества
JSON-Schema (`type`, `required`, `properties`, `items`, `minimum`,
`maximum`, `minLength`, `maxLength`, `enum`). Утверждения — декларативные
операторы (`eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `contains`, `len_gte`,
`len_lte`, `exists`) с путями только по ключам словаря; dunder-сегменты
запрещены.

**Тест-код никогда не исполняется в процессе API.** Он уходит в
`SandboxRunner` (subprocess-бэкенд с лимитами CPU/RAM/времени, как и
исполнение агентов). Если песочница недоступна — проверка получает
статус `error`, а не «пройдена».

### 3. Вердикт — агрегат

`task_verdicts` — одна строка на задание:

* все информативные проверки пройдены → `verified`;
* провалена авторитетная проверка (вес ≥ 1.5) или все провалены → `rejected`;
* есть и пройденные, и проваленные → `disputed`;
* нет информативных проверок (все `error`/`skipped`) → `unverified`.

Вердикт влияет на репутацию сильнее самого факта успеха: `verified` даёт
вклад источника `verification_passed` (вес 2.0), `rejected` —
`verification_failed` (вес 2.5). Провал наказывается строже, чем успех
поощряется, — это осознанный перекос в сторону осторожности.

### 4. Заявленное ≠ проверенное

`AgentCapability.declared_level` заполняет разработчик. `verified_level`
выставляет **только** сервис доверия, и только при условиях:

* не менее 2 вердиктов по агенту;
* доля подтверждённых (`verified`) среди решённых (`verified + rejected`)
  не ниже 80%;
* подтверждённый уровень **не выше** заявленного.

Если условия перестают выполняться (появились отказы), `verified_level`
сбрасывается в `NULL`. API отдаёт `trust_level`: `verified` / `declared` /
`unconfirmed`. Публичная выдача агента не смешивает эти поля.

### 5. Независимая проверка

`peer_agent` требует, чтобы у верификатора был **другой владелец**, чем у
исполнителя, и чтобы агент был опубликован. Проверка «сам себя» и
проверка агентом того же владельца отклоняются с разными кодами ошибок
(`self_verification_forbidden`, `verifier_not_independent`) — важно, чтобы
причина отказа была точной.

### 6. Отзывы

Один отзыв на задание, только от владельца задания, только по успешному
заданию. Оценка 1–5 переводится во вклад `(rating - 3) * 0.75`
(5★ → +1.5, 3★ → 0 — нейтральная оценка не создаёт события вовсе).
Флаг `confirm_result` добавляет отдельный вклад «владелец подтвердил
результат» с собственным `dedup_key`.

### 7. Аномалии и апелляции

Детектор (`detect_anomalies`) опирается только на наблюдаемые данные:

* `result_reuse` — одинаковый `result_hash` на разные входы;
* `rapid_results` — медиана длительности ниже 150 мс при ≥ 5 наблюдениях;
* `failure_spike` — доля отказов > 50% при ≥ 8 заданиях;
* `self_dealing` — агент фигурирует верификатором собственных заданий;
* `review_ring` — 3+ отзыва от одного пользователя.

Сигнал открывается один раз (уникальный `dedup_key` по агенту и типу),
сразу даёт отрицательный вклад. Админ может подтвердить сигнал (штраф
остаётся) или отклонить (вклад отзывается, репутация пересчитывается).

Апелляция открывается владельцем агента и рассматривается только
админом. При удовлетворении: дискредитированная проверка переводится в
`skipped`, связанные вклады отзываются, вердикт задания пересчитывается,
агенту начисляется компенсационный вклад источника `appeal`. При
отклонении — небольшой отрицательный вклад: апелляции не должны быть
бесплатным способом давления.

### 8. Совместимость

`gateway._update_agent_counters` больше не считает рейтинг сам: он
обновляет счётчики и вызывает `trust.on_task_finished`. Старая формула
удалена целиком, чтобы не было двух источников истины. Публичный
контракт `AgentPublic.reputation_score` не изменился.

## Последствия

**Плюсы**

* Любое число в интерфейсе объяснимо: `/agents/{id}/reputation` отдаёт
  разбивку по источникам и последние 10 вкладов.
* Проверки идемпотентны и не зависят от того, сколько раз клиент повторил
  запрос.
* Заявленные возможности нельзя «подтвердить» без фактических вердиктов.
* Накрутка репутации повторами, копипастом и взаимными отзывами
  обнаруживается и наказывается.

**Минусы и ограничения**

* Независимая проверка поддерживает только python-агентов-верификаторов;
  для внешних HTTP-верификаторов нужен отдельный контракт (этап 8).
* `cross_check` (перекрёстное сравнение двух исполнителей) объявлен в
  перечислении, но логики пока нет.
* Детектор аномалий — эвристики на SQL, без машинного обучения и без
  учёта сезонности; ложные срабатывания возможны и снимаются админом.
* Окно анализа ограничено 200 последними заданиями на признак.
* Репутация считается в Python после каждого вклада: для агента с
  десятками тысяч событий потребуется инкрементальный кэш (этап 9).

## Альтернативы

* **Средняя оценка отзывов вместо журнала вкладов.** Отклонено: не
  объясняет историю, уязвимо к накрутке, не учитывает проверки.
* **Внешний валидатор JSON-Schema (`jsonschema`).** Отклонено на этом
  этапе: нужен контроль над ошибками и отсутствие тяжёлой зависимости;
  подмножества достаточно для контрактов агентов. При росте требований
  заменяется адаптером.
* **Проверка тест-кода в процессе API.** Отклонено по требованию
  roadmap: недоверенный код не исполняется в основном backend.
* **Хранение рейтинга только в кэше без журнала.** Отклонено: теряется
  объяснимость и возможность пересмотра по апелляции.
