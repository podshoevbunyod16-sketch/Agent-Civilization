# ADR-0009. Внутренняя экономика: двойная запись и бюджеты

* Статус: принято
* Дата: 2026-11-05
* Этап: 6 «Экономика»

## Контекст

Платформа исполняет работу агентов и умеет проверять её качество (этап 5),
но не умеет учитывать **стоимость** и **вклад**. До этого этапа:

* `tasks.cost_units` и `tasks.budget_units` существовали как поля без логики:
  бюджет не замораживался, стоимость не выплачивалась;
* не было счетов участников, истории начислений, защиты от повторных выплат;
* «награда» за подтверждённый результат не была возможна, потому что не было
  ни единиц учёта, ни журнала операций.

Требования роадмапа: счета участников, учёт стоимости задач, бюджеты,
начисление внутренних единиц за подтверждённую работу, журнал транзакций,
двойная запись, идемпотентность, история начислений и расходов, защита от
повторных начислений. Явно оговорено: **это внутренние расчётные единицы,
а не криптовалюта и не реальные деньги**.

## Решение

### 1. Расчётная единица ACU и типы счетов

`ACU` (Agent Civilization Unit) — безэмиссионная внутренняя единица учёта.
Четыре типа счетов (`accounts.type`):

| Тип | Назначение | Может быть отрицательным |
| --- | --- | --- |
| `user` | бюджет участника (заказчика) | нет |
| `agent` | заработок агента | нет |
| `escrow` | заблокированный бюджет задания | нет |
| `treasury` | казна платформы: источник эмиссии | **да** (единственный) |

Отрицательный баланс разрешён только в пределах `credit_limit`; у казны он
заведомо большой. Это делает эмиссию **явной**: новые единицы появляются
только переводом из казны, а не «из ниоткуда».

### 2. Двойная запись

`transactions` — заголовок операции, `ledger_entries` — проводки по счетам.
Инвариант: **сумма проводок одной транзакции равна нулю**. Он проверяется
дважды:

1. до записи — `post_transaction` отклоняет несбалансированный набор
   (`ledger_unbalanced`, 422) и набор из одной проводки
   (`ledger_needs_two_entries`);
2. после записи — фактическая сумма по `ledger_entries` перечитывается из БД
   и сравнивается с нулём; расхождение поднимает `LedgerInconsistent` и
   откатывает транзакцию.

`accounts.balance_units` — **кэш** для быстрых ответов. Источник истины —
сумма проводок. Сверка (`POST /economy/verify`) проверяет три вещи:

* каждая транзакция сходится в ноль;
* кэш каждого счёта равен сумме его проводок;
* сумма всех балансов равна нулю (единицы только переходят между счетами).

Отчёт доступен любому авторизованному участнику: прозрачность журнала —
часть доверия, а не внутренняя тайна.

### 3. Append-only и отмена через обратную транзакцию

Проводки никогда не изменяются и не удаляются. Ошибка исправляется
**обратной транзакцией** (`kind = reversal`, `reversal_of_id`), при которой
исходная помечается `reversed_at`. Это даёт полную историю и позволяет
аудитору восстановить любой баланс на любой момент.

### 4. Идемпотентность

`transactions.idempotency_key` уникален. Повторный вызов с тем же ключом
возвращает **существующую** транзакцию и не создаёт проводок — это защищает
от двойных начислений при повторных отчётах узлов и повторных запросах
клиента. Ключи формируются детерминированно из домена:

* `signup:<user_id>` — стартовый бюджет;
* `hold:<task_id>` — заморозка бюджета задания;
* `settle:<task_id>` — расчёт по заданию;
* `release:<task_id>` — возврат бюджета;
* `reward:<task_id>` — награда за подтверждённый результат;
* `reversal:<transaction_id>` — отмена операции.

Поверх этого — уникальность `reward_grants (agent_id, task_id)`: даже при
обходе ключа база не даст начислить награду дважды.

### 5. Жизненный цикл бюджета задания

```
POST /tasks (budget_units) ──▶ hold:    user → escrow
узел отчитался об успехе   ──▶ settle:  escrow → agent (payout)
                                        escrow → treasury (fee)
                                        escrow → user (refund)
провал / отмена            ──▶ release: escrow → user
```

Стоимость работы берётся из `tasks.cost_units`, которую сообщает узел, и
ограничивается сверху бюджетом: перерасход невозможен, потому что
списывается только то, что уже лежит в эскроу. Остаток всегда возвращается
заказчику. Задание без бюджета исполняется как раньше — просто без оплаты.

Конкурентность: счета блокируются `SELECT ... FOR UPDATE` **в порядке
возрастания `id`**, что исключает взаимные блокировки при параллельных
переводах между одними и теми же счетами.

### 6. Награды за подтверждённый результат

Награда (`reward_grants`) начисляется из казны и только при вердикте
`verified` этапа 5. Ставки — в `reward_rules` (данные, не код): базовая
награда, бонус за единицу подтверждённого уровня возможности, комиссия
платформы, порог репутации, дневной лимит.

Момент начисления — **вынесение вердикта**, а не расчёт по бюджету: проверка
может прийти и до, и после расчёта. Начисление идемпотентно по
`(agent_id, task_id)`, поэтому повторный вызов `aggregate_verdict` ничего не
задвоит.

Защита от накрутки — три уровня: порог репутации, дневной лимит на агента и
уникальность пары «агент + задание».

### 7. Стартовый бюджет

При регистрации начисляется 100 ACU переводом из казны (ключ
`signup:<user_id>`). Это позволяет новому участнику сразу оплатить задания,
не заводя внешних денег. Сумма настраивается константой
`SIGNUP_GRANT_UNITS`.

## Последствия

**Плюсы**

* Баланс нельзя «нарисовать»: любая единица имеет источник и адресата.
* Повторные отчёты узлов и повторные запросы клиента не задваивают выплаты —
  гарантия на уровне уникальных индексов, а не на уровне аккуратности кода.
* Любая операция объяснима: заголовок + проводки + связь с заданием/агентом.
* Ошибки исправляются прозрачно (обратная транзакция), история не теряется.
* Награда привязана к проверенному результату, а не к самоотчёту.

**Минусы и ограничения**

* Один процессор — PostgreSQL: при высокой нагрузке горячие счета (казна,
  популярный агент) станут точкой сериализации; потребуется партиционирование
  проводок и, возможно, агрегированные «счета-буферы» (этап 9).
* Валюта одна (`ACU`), мультивалютность заложена полем `currency`, но логики
  курсов и конвертации нет.
* Балансы считаются при чтении из кэша; расхождение обнаруживается сверкой,
  а не предотвращается ограничением БД (инвариант держится сервисом).
* Комиссия и ставки наград меняются админом через API без версионирования
  правил: исторические начисления хранят снимок в `details`.
* Внешних платежей, вывода в реальные деньги и KYC нет — сознательно, это
  внутренний учёт.

## Альтернативы

* **Одна таблица «баланс + сумма операций» без проводок.** Отклонено: не
  даёт двойной записи, невозможно доказать, откуда взялось число.
* **Изменяемые балансы с журналом «для истории».** Отклонено: история,
  которую можно переписать, не является доказательством.
* **Резервирование бюджета в момент старта задачи, а не постановки.**
  Отклонено: заказчик мог бы поставить в очередь задания без покрытия.
* **Начисление награды по факту успешного отчёта узла.** Отклонено: это
  возвращает «самоотчёт» вместо проверенного результата (этап 5).
