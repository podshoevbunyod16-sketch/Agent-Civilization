# ADR-0007. Оркестрация: план как DAG шагов поверх существующего runtime

**Статус:** принято
**Дата:** 2026-11-06
**Контекст этапа:** 4 (Оркестрация)

## Контекст

Составное задание («исследуй рынок и сделай отчёт») не решается одним агентом:
нужна декомпозиция на шаги, зависимости между ними, подбор исполнителя под
каждый шаг и корректная обработка отказов. При этом этап 2 уже дал зрелый
runtime: очередь задач, аренда с fencing, лимиты, песочница, узлы.

Нужно добавить оркестрацию, не построив второй параллельный движок
исполнения (иначе появятся две несогласованные модели ретраев, лимитов и
аудита).

## Решение

### 1. План — отдельная сущность, шаг — обычное задание

`task_plans` (план) → `plan_steps` (шаги) → `tasks` (исполнение).
Каждый шаг связан с реальным `tasks.id`, поэтому лимиты, аренда, fencing,
песочница и события задания переиспользуются как есть. Оркестратор решает
только три вопроса: **что** запускать, **кем** и **когда**.

### 2. Подбор исполнителя — по возможностям, тем же скорингом, что и A2A

`assign_steps` использует `messaging.discover_agents`. Кандидат принимается
только при полном покрытии требуемых возможностей. Оценка соответствия
(`match_score`) сохраняется в шаге — это делает назначение объяснимым.

### 3. Готовность вычисляется, а не хранится вручную

Шаг `ready`, когда **все** зависимости `succeeded`. Провал зависимости
переводит шаг в `skipped` (при `fail_plan`) — «тихого» выполнения
полу-готового плана не бывает. Итог плана: все шаги `succeeded` →
`succeeded`, иначе `failed` с перечнем проблемных шагов.

### 4. Вход шага фиксируется снимком

`plan_steps.resolved_input` хранит ровно то, что получил исполнитель:
цель плана, собственный вход шага и **результаты зависимостей**. Это нужно,
потому что `output_payload` перезаписывается результатом задачи; без снимка
нельзя воспроизвести, на каких данных агент принимал решение. Ошибка,
найденная тестом: результаты зависимостей терялись при перезаписи.

### 5. Идентификаторы для человека

Ключи шагов (`key`) задаются человеком или планировщиком и уникальны в
рамках плана. API оперирует `step_key`, а не UUID: это делает URL и логи
читаемыми, а контракт декомпозиции — переносимым между языками.

### 6. Делегированная декомпозиция через A2A

План можно не описывать вручную: указывается `planner_agent_id`, и запрос
декомпозиции уходит агенту A2A-сообщением с контрактом `PlannerOutput`.
Ответ валидируется (формат, уникальность ключей, ацикличность) и
применяется **только после явного `POST /plans/{id}/adopt`**. Автоматическое
применение отклонено: агент — недоверенная сторона, его вывод не должен
менять план без решения пользователя.

### 7. Явные коды ошибок вместо общих

Ацикличность и существование зависимостей проверяет сервис, а не Pydantic,
чтобы клиент получал `cyclic_dependencies` / `unknown_dependency`, а не
`validation_error`. Это важно для планировщиков, которые автоматически
исправляют свои ответы по коду ошибки.

### 8. Возможности проверяются по формату, а не по таксономии

Реестр разрешает объявлять новые возможности, поэтому план не требует,
чтобы возможность уже была в таксономии. Отсутствие исполнителя — не ошибка
запроса, а состояние шага `blocked` с указанием причины.

## Последствия

**Плюсы**

* один движок исполнения: ретраи, лимиты и аудит не дублируются;
* назначение объяснимо (`match_score`, покрытые/недостающие возможности);
* вход каждого шага воспроизводим (`resolved_input`);
* декомпозиция может выполняться агентом на любом языке (JSON-контракт).

**Ограничения**

* продвижение плана требует вызова `POST /plans/{id}/run` (long-polling
  или планировщик); фоновый диспетчер не вводился, чтобы не усложнять
  развёртывание;
* параллелизм ограничен `max_parallelism` плана и слотами узлов;
* условные переходы (`if step failed then …`) не поддерживаются — только
  зависимости и политика отказа;
* результаты шагов хранятся в БД (JSONB); для больших артефактов нужен
  внешний storage (следующие этапы).

## Альтернативы

1. **Отдельный workflow-движок (Temporal/Cadence)** — отклонено на этом
   этапе: лишняя инфраструктура, PostgreSQL уже даёт нужные гарантии.
2. **Автоматическое принятие декомпозиции от агента** — отклонено:
   недоверенный вывод не должен менять план без подтверждения.
3. **Шаг как отдельная сущность без связи с `tasks`** — отклонено:
   пришлось бы дублировать аренду, лимиты, retry и аудит.
