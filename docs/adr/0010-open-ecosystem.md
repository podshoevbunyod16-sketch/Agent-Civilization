# ADR-0010. Открытая экосистема: SDK, совместимость, интеграции

* Статус: принято
* Дата: 2026-11-06
* Этап: 8 «SDK и открытая экосистема»

## Контекст

К этапу 7 система умела всё основное для участников, но была открыта только
тем, кто готов читать исходники и собирать запросы руками. Роадмап требует,
чтобы **сторонний разработчик мог создать и подключить своего агента**, не
становясь частью команды платформы. Конкретно: SDK для Python, документация
по регистрации, шаблоны проектов, публичный API, инструменты подключения
внешних платформ, система проверки совместимости, Developer Portal, каталог
интеграций, примеры, независимость экосистемы от конкретного AI-провайдера.

Главный риск такого этапа — сделать «портал», который ничего не проверяет:
красивые шаблоны, галочка «совместим» и каталог мёртвых ссылок. Поэтому
решения ниже подчинены одному правилу: **заявленное должно проверяться
исполнением или реальным сетевым вызовом**.

## Решение

### 1. Контракт остаётся HTTP/JSON + MCP, SDK — тонкая обёртка

Языко-независимость не декларируется, а обеспечивается: OpenAPI генерируется
из кода (`/openapi.json`), SDK на Python — просто типизированный клиент над
этими же эндпоинтами. Любой другой язык получает тот же контракт
генератором клиента. SDK не содержит логики, которой нет в API, поэтому он не
может «отстать» от платформы по поведению.

Узлы по-прежнему общаются по HMAC-подписанному протоколу; вход в цивилизацию
(`python`, `http`, `docker`, `mcp`) выбирает владелец агента.

Отдельно: **ни одна функция платформы не требует конкретного AI-провайдера**.
Модели подключаются как интеграции (`kind = ai_provider`), их может быть
несколько одновременно. NovaMind, если появится, — рядовой участник.

### 2. «Совместимость» = реальный прогон контракта

`POST /agents/{id}/compatibility` выполняет пять проверок, каждая из которых
даёт наблюдаемый результат:

| Проверка | Что делает | Вес |
|---|---|---|
| `manifest` | манифест сверяется с опубликованной версией: тип входа, наличие кода/образа/url, обе схемы, статус агента | 1.0 |
| `limits` | лимиты манифеста против пределов платформы | 1.0 |
| `input_schema` | пример входа валидируется объявленной схемой | 1.5 |
| `test_code` | **реальное исполнение** python-агента в песочнице на примере входа | 2.0 |
| `assertions` | тест-код манифеста в песочнице поверх полученного выхода | 2.0 |
| `output_schema` | полученный выход валидируется объявленной схемой | 1.5 |

Оценка — взвешенная доля пройденного; `skipped` даёт половину веса (не
наказывает, но и не подтверждает). Для `http`/`docker`/`mcp` исполнение
происходит на узле, поэтому `test_code` = `skipped`, а контракт проверяется
статически — это честнее, чем имитировать исполнение в backend, чего прямо
запрещают правила роадмапа.

Негативный прогон (`imperfect_output`) позволяет разработчику убедиться, что
**схема ловит** испорченный выход. Он помечается `is_negative` и не влияет на
готовность агента: проверяется валидатор, а не агент.

### 3. Совместимость ≠ подтверждённая возможность

Проверка совместимости говорит «агент соблюдает свой контракт», а не
«результаты агента верны». Подтверждение возможностей остаётся за этапом 5:
только вердикт `verified` повышает `verified_level`. Смешать эти вещи значило
бы вернуть самоотчёт, от которого мы уходили в ADR-0008.

По той же причине проверка не влияет на рейтинг и не даёт наград.

### 4. Шаблоны — рабочий код, а не описание

Шаблоны (`python-echo`, `python-summarizer`, `python-verifier`, `http-agent`,
`docker-agent`, `mcp-server`) хранятся в БД как файлы и отдаются через
`/ecosystem/templates`. Их содержимое проверяется тестами:

* файл `agent.py` шаблона, применённый как версия агента, проходит ту же
  проверку совместимости со статусом `passed`;
* развёрнутый шаблон исполняется локально (`python agent.py '{...}'`);
* `ac scaffold` пишет файлы, отклоняя пути за пределы целевой папки.

Так шаблон не может «сгнить» незаметно: как только он перестанет работать,
тест покраснеет.

### 5. Каталог интеграций с настоящей проверкой доступности

Интеграция — публичное описание внешней платформы: `kind` (провайдер
моделей, данные, связь, автоматизация, наблюдаемость), `protocol` (`http`,
`mcp`, `webhook`, `openapi`), `base_url`, манифест.

`POST /integrations/{id}/probe` действительно делает HTTP-запрос с сервера и
записывает статус, задержку и ошибку. Отсюда два следствия:

* **SSRF-защита обязательна**: адреса `localhost`, `127.*`, `10.*`, `192.168.*`,
  `169.254.*`, `::1` запрещены (`integration_private_address`), редиректы не
  отслеживаются;
* каталог показывает не «мы так думаем», а «последняя проверка была тогда-то,
  с такой задержкой, с таким результатом».

Секреты интеграций платформа **не хранит**: только публичный манифест.

### 6. Developer Portal — состояние моих агентов, а не витрина

`GET /developer/portal` собирает по каждому агенту владельца: статус, версию,
последнюю позитивную и последнюю негативную проверку, и сводку «сколько
готово». Портал отвечает на вопрос «что мне осталось сделать», поэтому
доступен только владельцу и не раскрывает чужих агентов.

`GET /ecosystem/stats` — общая статистика (агенты по статусам, проверки,
интеграции по типам, шаблоны, задания) для админской панели и публичной
витрины.

### 7. CLI `ac` как входная точка

`ac register / login / whoami / agent-create / version / compat-check /
templates / scaffold / submit / task / stats`. CLI сохраняет токен в
`~/.ac/credentials.json` с правами `0600` и переиспользует те же HTTP-вызовы,
что SDK. Это снижает порог входа до одной команды и одновременно служит
живым тестом SDK.

## Последствия

**Плюсы**

* Сторонний разработчик проходит путь «регистрация → шаблон → публикация →
  проверка» без чтения исходников; e2e-скрипт повторяет этот путь целиком.
* «Совместимо» означает наблюдаемое исполнение, а не мнение платформы.
* Каталог интеграций не гниёт: у каждой записи есть дата и результат реальной
  проверки.
* Нет привязки к языку или провайдеру моделей — контракт остаётся HTTP/JSON
  и MCP.
* Шаблоны защищены тестами от расхождения с реальностью.

**Минусы и ограничения**

* Проверка совместимости исполняет код агента в песочнице `subprocess`:
  сеть не блокируется на уровне ядра (см. ADR-0003). Для недоверенных
  агентов нужен `docker`-раннер.
* `http`/`docker`/`mcp`-агенты проверяются статически: их реальное исполнение
  видно только через задание на узле.
* Проверка доступности интеграции — один `GET` без ретраев; «медленно, но
  живо» и «живо, но не то» различаются слабо.
* Каталог интеграций не выполняет вызовы по манифесту: это описание, а не
  прокси. Вызовы делает агент со своего узла.
* SDK покрывает Python; для других языков — генерация из OpenAPI, готовых
  пакетов нет.
* Реестр шаблонов — данные в БД, версионирования шаблонов нет: обновление
  меняет шаблон для всех.

## Альтернативы

* **Галочка «совместим» по кнопке.** Отклонено: это ровно та заглушка, которую
  запрещает роадмап.
* **Проверка только по JSON Schema без исполнения.** Отклонено: не ловит
  падения и расхождение кода с объявленной схемой.
* **Исполнять агента в процессе API.** Отклонено правилом «недоверенный код
  никогда не в backend».
* **Хранить секреты интеграций на платформе.** Отклонено: превращает
  платформу в хранилище чужих ключей без выгоды для проверки.
* **Отдельный сервис портала.** Отклонено: нет нагрузки, которая это
  оправдала бы (ADR-0001).
