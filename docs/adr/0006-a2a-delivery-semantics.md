# ADR-0006. Семантика доставки A2A-сообщений

**Статус:** принято
**Дата:** 2026-11-06
**Контекст этапа:** 3 (Коммуникация)

## Контекст

Агентам нужно обмениваться сообщениями: запрос → ответ, события, вызовы
инструментов MCP. Участники живут в разных местах: HTTP-эндпоинты
(внешние агенты), python-код в песочнице, MCP-серверы. Сеть ненадёжна,
процессы падают, часть агентов отвечает медленно. При этом система должна
масштабироваться на несколько реплик API и несколько воркеров доставки
без координатора.

Ограничения, которые нельзя нарушать:

* API-процесс не должен выполнять недоверенный код и не должен делать
  исходящие вызовы к чужим агентам (ADR-0003);
* агент может ответить дважды или не ответить вовсе;
* пользовательские данные (диалоги) не должны утекать между владельцами;
* API остаётся stateless (ADR-0005), состояние — в PostgreSQL/Redis.

## Решение

### 1. Очередь в PostgreSQL, а не отдельный брокер

Сообщение — строка `agent_messages` со статусом
`pending → processing → delivered | failed | expired`. Отдельный брокер
(Kafka/RabbitMQ) не вводится: на текущем масштабе он добавляет операционную
сложность без выигрыша. Очередь выбирается запросом

```sql
SELECT ... FROM agent_messages
WHERE status IN ('pending','processing')
  AND (next_attempt_at IS NULL OR next_attempt_at <= now())
  AND (locked_until IS NULL OR locked_until <= now())
ORDER BY created_at
LIMIT :n
FOR UPDATE SKIP LOCKED;
```

`SKIP LOCKED` даёт естественное распределение между воркерами без
координатора: каждый берёт только свободные строки.

### 2. Аренда (lease) вместо «вечной» блокировки

При захвате воркер ставит `locked_until = now() + 120s`. Если он умер,
аренда истекает и сообщение снова доступно — это и есть гарантия
**at-least-once**. Альтернатива с блокировкой до явного подтверждения
приводила бы к «застрявшим» сообщениям после падения воркера (проверено
тестом `test_claim_returns_message_with_assignment`).

Аренда хранится в отдельной колонке, а не в `error`/`details`: служебные
поля не должны попадать в публичные ответы API.

### 3. Идемпотентность отправки — на уровне БД

`UNIQUE (sender_agent_id, idempotency_key)`. Повтор с тем же ключом
возвращает существующее сообщение с `is_duplicate=true` и кодом 201,
а не создаёт дубль и не отдаёт ошибку: отправитель не должен различать
«повтор после таймаута» и «первый успешный вызов».

### 4. Повторы и срок жизни

* `max_attempts` (по умолчанию 3) — после исчерпания статус `failed`;
* задержка `min(2^attempt, 300)` секунд — защита от «шторма» повторов;
* `expires_at = created_at + timeout_seconds` — сообщение не доставляется
  после истечения срока (`expired`), даже если попытки остались.

### 5. Доставку выполняет отдельный воркер

Backend только ставит сообщение в очередь и отдаёт задание через
внутренний API `/internal/messages/*`, защищённый `X-Service-Token`
(сравнение в постоянное время, fail-closed при пустом токене). Воркер
`app/worker/message_worker.py` — единственный компонент, который:

* делает исходящие HTTP-вызовы к агентам;
* запускает python-агентов в песочнице (переиспользуется `SandboxRunner`);
* вызывает MCP-инструменты по JSON-RPC.

Воркеров можно запускать сколько угодно и где угодно: они не хранят
состояние, а только забирают и отчитываются о сообщениях.

### 6. Стратегия доставки выводится из точки входа

| Точка входа агента | Стратегия | Кто выполняет |
|---|---|---|
| `http` | `http` | воркер: POST `{"input": payload}` |
| `python` / `docker` | `sandbox` | воркер: `SandboxRunner` с лимитами версии |
| MCP-сервер агента | `mcp` | воркер: `initialize → tools/call` |
| нет точки входа | `inbox` | никто, сообщение лежит в inbox |

Явно указанная стратегия в запросе имеет приоритет, но должна быть
подкреплена точкой входа (иначе `422`), чтобы нельзя было «попросить»
MCP у агента без MCP-сервера.

### 7. Ограничение глубины цепочки

`MAX_CHAIN_DEPTH = 12`: два вежливых агента не должны разговаривать
бесконечно и жечь бюджет. При превышении — `422 chain_depth_exceeded`.

### 8. События реального времени

Каждое изменение статуса публикуется в шину событий (`conversation:{id}`),
поэтому WebSocket-поток диалога работает при нескольких репликах API
(Redis Pub/Sub, ADR-0005). Публикация не критична для доставки: ошибки
шины логируются, но не откатывают транзакцию — источник истины в БД.

### 9. MCP: токен не покидает сервер

`auth_token` MCP-сервера хранится в `mcp_servers.auth_token`, в API
сериализуется только флаг `has_auth_token`. Инструменты видны только
владельцу агента; посторонним отдаются пустой список и `has_auth_token=false`.

## Последствия

**Плюсы**

* нет отдельного брокера — меньше инфраструктуры при сохранении
  горизонтальной масштабируемости;
* at-least-once без координатора и без «застрявших» сообщений;
* backend изолирован от недоверенных вызовов (соответствует ADR-0003);
* идемпотентность и дедупликация — на уровне БД, а не в памяти процесса.

**Минусы / ограничения**

* доставка **at-least-once**, а не exactly-once: получатель должен быть
  идемпотентным по `idempotency_key`/`message_id` (это документируется
  в SDK и API);
* `FOR UPDATE SKIP LOCKED` ограничивает пропускную способность одного
  воркера; при росте нагрузки очередь выносится в отдельное хранилище
  (партиционирование по `created_at` или внешний брокер);
* задержка доставки зависит от интервала опроса воркера (по умолчанию 1 с);
* при отсутствии Redis события реального времени не доходят до других
  реплик (локальная шина работает только внутри процесса).

## Альтернативы

1. **Kafka/RabbitMQ** — отклонено: лишняя инфраструктура, нет потребности
   в сохранении истории событий на текущем этапе.
2. **Redis Streams** — отклонено: сообщения должны иметь явные связи с
   агентами и диалогами, транзакционность с PostgreSQL важнее скорости.
3. **Синхронный вызов агента в API-процессе** — отклонено: нарушает
   изоляцию недоверенного кода и превращает медленного агента в отказ
   всего API.
