# ADR-0004: Очередь заданий на pull-модели с арендой и fencing

**Статус:** принято · **Дата:** 2026-11-05

## Контекст

Задания должны выполняться на узлах участников, которые находятся за NAT,
могут отключаться и работать нестабильно. Нужна надёжная доставка без
потери задач и без двойного выполнения бизнес-операций.

## Решение

* **Pull-модель:** узел сам запрашивает задания (`POST /nodes/me/tasks/claim`).
  Исходящие соединения нужны только узлу — проброс портов не требуется.
* **Аренда (lease):** при выдаче задачи создаётся `lease_token` на 60 секунд,
  продлевается прогресс-репортами. Истёкшая аренда возвращает задачу в очередь.
* **Fencing:** результат принимается только от пары `(node_id, lease_token)`;
  чужой узел или старая аренда получают `403`/`422`.
* **Безопасный захват:** `SELECT ... FOR UPDATE SKIP LOCKED` — несколько
  воркеров не мешают друг другу, блокировок нет.
* **Идемпотентность:** `idempotency_key` на задачу, `result_hash` (sha256)
  как основа будущей верификации.
* **Ретраи:** до `max_attempts`, ошибка сохраняется в `tasks.error`.

## Обоснование

* Pull + lease — стандартная схема для нестабильных исполнителей (как в
  Celery/SQS, но без внешнего брокера: PostgreSQL уже источник истины).
* Fencing решает проблему «медленного узла»: опоздавший результат отвергается,
  а не затирает корректный.
* Нет отдельной инфраструктуры брокера → проще деплой и меньше точек отказа.

## Последствия

* (+) Узлы за NAT, устойчивость к падениям, отсутствие двойного выполнения.
* (+) Прозрачный жизненный цикл: все переходы в `task_events`.
* (−) Задержка до `poll_interval` при появлении задачи.
  Смягчение: Pub/Sub-уведомление узлу — кандидат на этап 3.
* (−) Очередь живёт в PostgreSQL: при экстремальной нагрузке потребуется
  отдельный брокер (этап 9), интерфейс шлюза это позволяет.
