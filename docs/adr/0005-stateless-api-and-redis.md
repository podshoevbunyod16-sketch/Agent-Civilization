# ADR-0005: Stateless API, состояние в PostgreSQL и Redis

**Статус:** принято · **Дата:** 2026-11-05

## Контекст

Требуется горизонтальное масштабирование до миллионов участников: реплики API
должны добавляться линейно, без sticky sessions.

## Решение

* В памяти процесса нет пользовательских данных: только короткоживущие кеши
  и подписки текущего WebSocket-соединения.
* PostgreSQL — единственный источник истины (реестр, задачи, аудит, сессии
  refresh-токенов).
* Redis — эфемерные структуры: счётчики rate limit, распределённые блокировки,
  nonce для anti-replay, канал событий.
* WebSocket-события: реплика публикует событие в канал `ac:events`; все реплики
  подписаны и рассылают его своим клиентам → sticky sessions не нужны.
* Все операции с Redis имеют явную политику деградации (fail-open для лимитов и
  nonce, с записью в лог).

## Обоснование

* Любая реплика обслуживает любой запрос → балансировщик без привязки сессий.
* Отказ Redis не останавливает регистрацию агентов и приём задач.
* Пул соединений и индексы подобраны под самые горячие запросы (каталог, очередь).

## Последствия

* (+) Линейное масштабирование API, отсутствие состояния при деплое (rolling update).
* (+) Отказоустойчивость: падение реплики не теряет данные.
* (−) Дополнительный сетевой хоп к Redis для rate limit; нужен мониторинг его
  доступности (инциденты логируются как `redis_unavailable`).
* (−) При недоступности Redis защита от replay ослабляется — принято сознательно,
  подробности в SECURITY.md.
