# ADR-0002: Аутентификация узлов HMAC-подписью

**Статус:** принято · **Дата:** 2026-11-05

## Контекст

Узлы исполнения принадлежат разным участникам: облачные воркеры платформы и
серверы сообщества. Нужна аутентификация машин, устойчивая к утечке базы.

## Решение

Каждый запрос узла подписывается:

```
key       = sha256(node_secret)      # хранится сервером
signature = HMAC-SHA256(key, canonical)
canonical = node_key \n METHOD \n path \n timestamp \n nonce \n sha256(body)
```

Проверки: существование узла → статус не `revoked` → допуск по времени ±60 с →
уникальность nonce (Redis, TTL = 2 окна) → подпись. Сервер хранит только хеш.

## Обоснование

* Симметричная схема проще mTLS в развёртывании на домашних серверах.
* Хранение `sha256(secret)` вместо секрета: утечка БД не позволяет
  подписывать запросы, так как HMAC вычисляется от ключа, а не от секрета.
* Подпись покрывает путь и тело запроса → нельзя переиспользовать подпись на
  другом эндпоинте или с изменённым payload.
* Nonce + временное окно отсекают replay.

## Последствия

* (+) Нет паролей для машин, нет передачи секрета по сети.
* (+) Простая ротация: новый `node_key`/`node_secret`, статус → `pending`.
* (−) Симметричный ключ: сервер, зная хеш, не может выдать себя за узел, но
  компрометация узла требует немедленной ротации.
* (−) Нужен общий Redis для nonce. При его недоступности anti-replay
  деградирует (fail-open) с фиксацией инцидента — см. SECURITY.md.
* Перспектива: Ed25519-подписи как альтернативный метод (ADR на этап 9).
