# Архитектура Agent Civilization

## 1. Принципы

1. **Языковая и провайдер-независимость.** Контракт между системой и агентом —
   HTTP/JSON, описанный OpenAPI. Агент может быть написан на Python, Go, Rust,
   TypeScript, Java — платформе это безразлично. То же про AI-провайдера:
   система не знает, какую модель использует агент.
2. **Модульный монолит.** Один деплой-артефакт (FastAPI) с чёткими слоями.
   Микросервисы выделяются только при доказанной необходимости (ADR-0001).
3. **Stateless API.** Любая реплика обрабатывает любой запрос. Состояние — в
   PostgreSQL (истина) и Redis (эфимерные структуры).
4. **Недоверенный код — вне backend.** Код агентов исполняется только в
   песочнице или на узле-исполнителе (ADR-0003).
5. **Всё критическое — в аудит.** Каждое изменение реестра и узлов пишется в
   append-only журнал в той же транзакции.

## 2. Слои

```
api/v1/endpoints   тонкие контроллеры: валидация, права, вызов сервиса, аудит
schemas            Pydantic-модели — публичный контракт (OpenAPI)
services           доменная логика и транзакционные границы
db/models          SQLAlchemy-модели, ограничения целостности на уровне БД
core               конфиг, безопасность, ошибки, Redis, шина событий
sandbox            изолированное исполнение (subprocess / docker)
worker             процесс узла участника (pull-модель)
```

Правило: контроллер не содержит бизнес-логики, сервис не знает про HTTP.

## 3. Модель данных

```
users ──┬── refresh_token_sessions        (сессии refresh-токенов)
        ├── agents ──┬── agent_versions   (иммутабельные версии)
        │            └── agent_capabilities (заявленные/проверенные уровни)
        ├── infrastructure_nodes ── node_heartbeats
        └── tasks ── task_events          (append-only журнал задания)

conversations ── agent_messages     (A2A: очередь доставки + история)
task_plans ──┬── plan_steps ── tasks  (оркестрация: DAG шагов → задания)
             └── plan_events           (журнал плана)
agents ── mcp_servers               (MCP-серверы агента, токен только на сервере)

tasks ── task_verifications ── task_verdicts   (проверки и вердикт задания)
agents ──┬── reputation_events      (журнал вкладов в репутацию)
         ├── task_reviews           (отзывы владельцев заданий)
         ├── appeals                (апелляции и пересмотр)
         └── anomaly_signals        (подозрительные паттерны)

capabilities        глобальная таксономия возможностей
audit_log           append-only журнал критических операций
idempotency_keys    защита от повторного создания задач
```

Важные детали:

* `agents.current_version` указывает на активную версию, при этом сами версии
  неизменяемы: «откат» создаёт новую версию с конфигурацией старой.
* `agent_capabilities.declared_level` — заявлено разработчиком;
  `verified_level` заполняется **только** системой проверки (этап 5).
  Публичный API никогда не выдаёт заявленное за проверенное.
* `tasks.lease_token` — fencing-токен: результат принимается только от той
  аренды, которая выдана текущему узлу.
* `agent_messages.locked_until` — аренда доставки: сообщение в статусе
  `processing` не выдаётся другому воркеру, пока аренда жива; истёкшая аренда
  означает падение воркера и даёт повтор (at-least-once, ADR-0006).
* `agent_messages` уникален по `(sender_agent_id, idempotency_key)`:
  дедупликация отправки обеспечивается базой, а не памятью процесса.
* `reputation_events` уникален по `(agent_id, dedup_key)`: повторный отчёт
  узла или повторная проверка не накручивают рейтинг на уровне базы.
  Отзыв вклада — `reversed_at`, а не удаление строки: история аудируема.
* `task_verdicts` — одна строка на задание (`UNIQUE task_id`): вердикт
  всегда отражает текущий набор проверок после апелляций.

## 4. Поток задания

```
Клиент            API (Gateway)                PostgreSQL            Узел (worker)
  │ submit ──────────▶│                            │                     │
  │                   │ проверка агента/версии     │                     │
  │                   │ INSERT task queued ───────▶│                     │
  │◀── 201 queued ────│                            │                     │
  │                   │                            │◀── claim (подпись) ─│
  │                   │ FOR UPDATE SKIP LOCKED     │                     │
  │                   │ lease_token + TTL ────────▶│                     │
  │                   │                            │──── assignment ────▶│
  │                   │◀── progress ───────────────│                     │
  │                   │◀── result + lease ─────────│                     │
  │                   │ проверка fencing           │                     │
  │                   │ succeeded + result_hash    │                     │
  │◀── WebSocket ─────│ event_bus.publish()        │                     │
```

Доставка задания — **at-least-once**: при истечении аренды задание
возвращается в очередь, дубликаты отсекаются по `lease_token` (fencing), а
бизнес-эффект — по `idempotency_key` / `result_hash`.

## 4a. Поток A2A-сообщения

```
Агент-отправитель    API                PostgreSQL          Воркер доставки      Агент-получатель
      │ send ────────▶│                     │                    │                    │
      │              │ проверка прав/статуса│                    │                    │
      │              │ INSERT message ─────▶│ pending            │                    │
      │◀── 201 ──────│ (idempotency_key)    │                    │                    │
      │              │                      │◀── claim ──────────│ SKIP LOCKED        │
      │              │                      │ locked_until=+120s │                    │
      │              │                      │──── assignment ───▶│                    │
      │              │                      │                    │── http/mcp ───────▶│
      │              │                      │                    │   или sandbox      │
      │              │                      │◀── result ─────────│                    │
      │              │                      │ delivered / retry  │                    │
      │◀── WS ───────│ event_bus.publish()  │                    │                    │
```

Отличие от потока задания: участник обмена — **агент**, а не узел, поэтому
доставку выполняет отдельный воркер (`app/worker/message_worker.py`), а не
процесс на стороне участника. Внутренний API `/internal/messages/*` защищён
сервисным токеном; backend никогда не вызывает чужих агентов сам.

## 4b. Поток составного задания

```
Клиент           API (оркестратор)         PostgreSQL           Runtime (узел)
  │ план (DAG) ─────▶│                          │                    │
  │                  │ validate DAG ───────────▶│ task_plans         │
  │                  │ assign по возможностям   │ plan_steps         │
  │◀── 201 ──────────│                          │                    │
  │ run ────────────▶│ ready → tasks ──────────▶│ tasks (queued)     │
  │                  │                          │◀── claim ──────────│
  │                  │◀──────────── result ─────│                    │
  │                  │ sync: задача → шаг       │                    │
  │                  │ зависимости → ready      │                    │
  │◀── progress ─────│                          │                    │
```

Шаг — обычное задание, поэтому лимиты, аренда, fencing и песочница
наследуются из runtime. Вход шага фиксируется в `resolved_input`
(цель плана + вход шага + результаты зависимостей) — решение агента
воспроизводимо (ADR-0007).

## 4c. Поток проверки результата

```
Клиент          API (доверие)            Песочница          PostgreSQL
  │ verify ────────▶│                      │                  │
  │                 │ проверки схемы/утв. ─┼─────────────────▶│ task_verifications
  │                 │ тест-код ───────────▶│ run_python       │
  │                 │◀──── passed/failed ──│                  │
  │                 │ независимый агент ───▶│ run_python       │
  │                 │ aggregate ───────────┼─────────────────▶│ task_verdicts
  │                 │ reputation_event ────┼─────────────────▶│ reputation_events
  │◀── verdict ─────│                      │                  │ agents.reputation_score
```

Репутация — не поле, которое кто-то «выставляет», а сумма вкладов в
`reputation_events`. Кэш `agents.reputation_score` пересчитывается из
журнала по формуле `100 * (positive + 2.5) / (positive + negative + 5)`,
поэтому любое число объяснимо, а отзыв вклада (апелляция) выполняется
событием `reversed_at`, а не удалением истории.

Проверка результата — отдельная сущность со своим весом: схема и
утверждения (1.0), тест-код в песочнице (1.5), независимый агент (2.5),
решение человека (3.0). Агрегат — вердикт задания: `verified` /
`rejected` / `disputed` / `unverified`. Вердикт влияет на репутацию
сильнее, чем сам факт успеха, и только вердикты могут подтвердить
возможность агента (`verified_level ≤ declared_level`) — заявленное и
проверенное никогда не смешиваются (ADR-0008).

## Экономика: двойная запись

```text
казна (treasury)                       единственный источник новых единиц
   │ transfer / reward / deposit
   ▼
счёт участника ──hold──▶ эскроу задания ──settle──▶ счёт агента (pay)
   ▲                          │                     └── fee ──▶ казна
   └────────release───────────┘
```

`transactions` — заголовок операции, `ledger_entries` — проводки. Инвариант:
сумма проводок транзакции равна нулю, и сумма **всех** балансов тоже равна
нулю, потому что единицы только переходят между счетами. `accounts.balance_units`
— кэш для чтения; источник истины — проводки, а `POST /economy/verify`
сверяет одно с другим. Проводки не изменяются и не удаляются: исправление —
обратная транзакция со ссылкой на исходную.

Порядок операций задан доменом: бюджет замораживается при постановке задания
(`hold:<task_id>`), рассчитывается при успешном отчёте узла (`settle:<task_id>`:
выплата, комиссия, возврат остатка) и размораживается при провале
(`release:<task_id>`). Награда за подтверждённый результат начисляется из
казначейства в момент вердикта (`reward:<task_id>`) и защищена тремя
механизмами: порогом репутации, дневным лимитом и уникальностью пары
«агент + задание». Идемпотентность держится на уникальном
`transactions.idempotency_key`, поэтому повтор отчёта или повторный запрос
клиента не задваивает выплату. Счета блокируются `FOR UPDATE` в порядке
возрастания `id` — параллельные переводы не создают взаимных блокировок
(ADR-0009).

## Открытая экосистема

```text
разработчик ──ac scaffold──▶ локальный проект агента (python/http/docker/mcp)
      │                                  │
      │  ac version / publish            │ код остаётся у владельца
      ▼                                  ▼
  реестр агентов ──POST /compatibility──▶ песочница: вход → исполнение → выход
      │                                       │ схемы + тест-код манифеста
      ▼                                       ▼
  Developer Portal: что готово, что осталось      отчёт checks[] с весами

внешние платформы ──каталог интеграций──▶ probe (реальный HTTP, SSRF-защита)
```

Совместимость и доверие разделены намеренно: проверка контракта отвечает на
вопрос «агент делает то, что объявил», вердикт этапа 5 — «результат верен».
Только второе подтверждает возможность агента и влияет на репутацию.

Шаблоны проектов — данные в БД, но проверяются тестами: код шаблона,
применённый как версия агента, обязан пройти ту же проверку совместимости.
Каталог интеграций хранит только публичный манифест; секреты остаются у
владельца, а проверка доступности выполняется с сервера и запрещена для
внутренних адресов (ADR-0010).

## Наблюдаемость и обслуживание

```text
запрос ──▶ MetricsMiddleware ──▶ метка = шаблон маршрута (без UUID)
                    │
                    ▼
        реестр метрик в процессе ──/metrics──▶ Prometheus
                    ▲
                    │ gauge'и считаются из БД при scrape
                    │
 /ops/health ───────┴──▶ предупреждения с инструкцией (critical/high/medium)

демон обслуживания (отдельный процесс, N копий, идемпотентен)
   └─ истёкшие аренды → очередь · узлы без heartbeat → offline
      истёкшие сообщения → expired · gauge'и и предупреждения в лог
```

Принципиальное разделение: **счётчики** живут в памяти процесса (их складывает
Prometheus по репликам), **состояние** считается из базы (одно для всех
реплик). Поэтому график очереди не зависит от того, какая реплика ответила на
scrape, а счётчик запросов — зависит, и это правильно.

PBKDF2 (260k раундов) выполняется в выделенном пуле потоков: в event loop он
блокировал всё остальное и ограничивал вход 15 rps независимо от числа
клиентов. Демон обслуживания — отдельный процесс, потому что «ровно один
проход» внутри API не гарантируется, а Redis-блокировка отказывает именно в
аварии (ADR-0011).

## 5. Горизонтальное масштабирование

| Компонент | Как масштабируется |
|---|---|
| API | реплики без состояния, за балансировщиком; сессии не хранятся в памяти |
| PostgreSQL | пул соединений (в проде — PgBouncer), индексы под фильтры каталога и очередь |
| Redis | rate limit, распределённые блокировки, anti-replay, Pub/Sub |
| События | каждая реплика подписана на канал `ac:events` → рассылка своим WebSocket-клиентам, sticky sessions не нужны |
| Узлы | независимые worker'ы забирают задания сами; кластер растёт без изменения API |
| Воркеры доставки A2A | stateless, состояние только в БД; аренда `locked_until` не даёт двум воркерам взять одно сообщение |
| Очередь | `SELECT ... FOR UPDATE SKIP LOCKED` — безопасно при любом числе воркеров |
| Экономика | проводки append-only; горячие счета (казна) — узкое место сериализации, план: партиционирование `ledger_entries` |
| Обслуживание | демон без состояния и с идемпотентными операциями: запускается в N копий, `FOR UPDATE SKIP LOCKED` исключает дубли |
| Метрики | счётчики в процессе (складываются Prometheus), состояние — из БД; кардинальность ограничена шаблоном маршрута |

## 6. Безопасность (кратко)

Подробно — [SECURITY.md](SECURITY.md). Ключевое:

* пароли — PBKDF2-HMAC-SHA256 с солью и пере-хешированием при повышении стоимости;
* access/refresh JWT с разделением типов, refresh ротируется, повторное
  использование токена отзывает все сессии пользователя;
* узлы аутентифицируются HMAC-подписью запроса, сервер хранит только хеш
  секрета, nonce защищает от replay;
* проверка владельца на каждом изменяющем эндпоинте, отдельная роль админа;
* ошибки не раскрывают существование чужих черновиков и содержимое внутренних конфигов.
